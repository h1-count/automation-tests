# 参数组合设计（pairwise）速查

参数组合设计的任务：把"输入项 × 取值"压成**有依据、可复查**的一小组数据行，而不是拍脑袋挑几条，也不是全组合硬跑。方法源自 PICT（Pairwise Independent Combinatorial Testing，[microsoft/pict](https://github.com/microsoft/pict)）。

## 1. 何时用哪种规模（统一触发规则）

有效组合数一律按**业务约束过滤后**计算，不是全组合原始规模。判定结论逐对象登记进功能包 `scope.json` 的 `combinationDesign`（策略、理由、参数与取值依据、约束、有效组合数；pairwise 另登记模型路径、摘要与 D 编号），缺失或选错会阻断完整性审计、Excel 导出与 `npm run test:fast`。

| 参数情况（按约束过滤后） | 策略 |
| --- | --- |
| 参数间无交叉影响（含纯展示、单状态对象） | `not_applicable`：不填参数，有效组合数为 0 |
| 参数 ≤ 2 个（任意有效组合数），或任意参数数下有效组合 ≤ 12 条 | `direct_enumeration`：直接全组合（通常 ≤ 9 行），不需要工具，逐行映射数据编号 |
| 参数 ≥ 3 个且有效组合 > 12（典型：4×4×3×3=144，约束剔除后仍超 12） | `pairwise`：覆盖**任意两个参数的所有取值对**，行数通常是十几条，压缩 80–90% |
| 关键安全/资金路径 | 在 pairwise 之外**手工补**全组合中最危险的几行（如"全部非法输入同时出现"），不要指望 pairwise 覆盖三路、四路交互——补充用例以 `manualSupplementCaseIds` 登记进 `combinationDesign`，只读对象可改给 `manualSupplementReason` 范围外理由 |

## 2. 建模四步

1. **列参数**：输入框、下拉/单选、开关、上传项、前置状态（登录/未登录）。给业务名：`登录方式`、`凭证有效性`、`协议勾选`。
2. **压取值**：等价类划分 + 边界值。长度上限 6 → `0、1、5、6、7` 五个取值而不是枚举所有串；格式校验 → `合法 / 非法字符 / 空`。负向取值是重点，别只写合法路径。
3. **写约束**：参数间的真实业务依赖。约束必须有业务理由，写进注释或命名。
4. **跑生成器**：`node skills/testcase-designer/scripts/pict-pairwise.mjs --model <model.json> --format md`，核对输出行与覆盖率。

## 3. 模型 JSON 语法

```json
{
  "parameters": {
    "登录方式": ["账号密码", "短信验证码"],
    "凭证": ["有效", "无效"],
    "协议": ["已勾选", "未勾选"],
    "历史失败次数": ["0", "3", "4"]
  },
  "exclude": [
    ["登录方式=短信验证码", "凭证=无效"]
  ],
  "ifThen": [
    { "if": "历史失败次数=4", "then": "协议=已勾选" }
  ]
}
```

- `parameters`：保序对象，输出列顺序与此一致；
- `exclude`：禁止组合。每条是若干 `参数=值` 原子，**一行同时包含全部原子即被剔除**。业务规则"短信登录不校验密码凭证"→ `["登录方式=短信验证码", "凭证=无效"]`；
- `ifThen`：`IF` 原子成立时 `THEN` 参数只允许列出的取值（逗号分隔），其余取值组合全部剔除。等价于 PICT 的 `IF [A]="a" THEN [B] IN {…};`。上例：失败 4 次进入锁定流程，必须勾选协议才能继续；
- 原子引用的参数、取值必须真实存在，否则脚本报错；
- 全组合上限 200 000：超限说明等价类没压够，或该拆成多个独立模型（互不交互的参数分开建模）。

## 4. 输出 → 用例表的映射

生成器输出形如：

```
| # | 登录方式 | 凭证 | 协议 | 历史失败次数 |
| 1 | 账号密码 | 有效 | 已勾选 | 0 |
| 2 | 短信验证码 | 有效 | 未勾选 | 4 |
…
```

映射规则：

1. 每行分配一个数据编号 `D01`、`D02`……与步骤表"数据编号"列对应；
2. 同一参数化用例的多行步骤共享同一 `dataId`（如填表步骤与提交步骤都用 `D03`）；在 cases.md 折叠正文或前置条件里注明“参数化数据 D01~Dnn 由 pairwise 生成，模型见 `runtime/pairwise/pict-model.json`”；
3. 每行数据都要在步骤表里有**明确预期**——pairwise 只给组合，不给判定；预期从需求逐条推导（这是设计工作的本体，工具替代不了）;
4. 含写入动作的组合行（如"提交注册"）单独拆成高风险用例，不要混在校验用例里。

## 5. 检查清单

- [ ] 每个参数的取值覆盖：合法、非法、空、边界（上限、上限+1）；
- [ ] 约束都有业务理由；输出末尾"被约束整体排除…（属预期）"列出的对应与业务规则一一对应；
- [ ] `scope.json` 的 `combinationDesign` 已登记：策略 `pairwise`、按约束过滤后的有效组合数（与生成器 `statistics.validCombos` 一致）、模型路径与 sha256 摘要、`D01…Dnn` 全列、人工补充用例或范围外理由；
- [ ] 退出码：`0` 正常；`2` 表示存在"可覆盖取值对未被覆盖"的告警——正常不应出现，出现即模型或用法异常，先核对参数/取值/约束拼写；
- [ ] 输出行数 ≈ 最大两参数取值数乘积量级（4×4 参数典型 12~20 行）；行数异常大通常是约束太少或取值没压缩；
- [ ] 危险组合（多负向叠加、资金、写入）已手工补齐并标注来源"手工补充"；
- [ ] `testpacks/<type>/<project>/<feature>/runtime/pairwise/pict-model.json` 保留在所属功能包 `runtime/`（不入 Git），路径与摘要登记进可提交的 `scope.json`，用例表里引用其路径。
