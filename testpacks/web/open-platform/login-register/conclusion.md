# 开放平台登录与注册：测试结论

## 当前结论

- 用例集共 25 条（工作簿口径，对应 23 条可执行测试：004/005/019 合并为单条注册成功链路），2026-09-02 全部实现并通过。本轮（2026-09-02 凭据初始化补录轮）新增 OP-AUTH-024/025，原"账号密码登录成功路径"待确认行正式关闭；此前一轮（2026-09-02 对象矩阵核对）曾新增 022/023 并为 002 补「已登录回访登录页」步骤（依据 `src/permission.ts`、`src/routes/common.ts`、`RegisterForm.vue` 源码核实，MCP 探索复核一致）。
- **凭据初始化方案（2026-09-02，本轮核心）**：源码核实注册流程无密码环节（`CompanyRegisterForm` 12 字段无 password），账号密码由「手机号+短信验证码+新密码」重置链路设置（`ResetPassword.vue` → `forgetPassword` API）——三要素均在测试可控范围。024 以重置链路自助初始化测试账号密码（合成值仅写本地 `.env` 的 `TEST_PASSWORD`，不入 Git/报告/日志/台账，重复执行幂等重设），025 用该密码实证账号密码登录成功路径，不再依赖用户提供凭据。
- **024 实证（2026-09-02，18.7s）**：登录页「忘记密码」→ `/reset-pw`；测试手机号请求重置验证码（人工过图形验证码）；固定测试验证码 + 合成密码提交 → 「重置成功，请重新登录！」提示 → 确认后跳转登录页。
- **025 实证（2026-09-02，1.4m）与执行探索新页面事实**：账号密码登录在**未验证过的设备/浏览器档案**上首次使用时，登录接口返回 `loginType=1`（`isFirstLoginResp`），前端切换「首次设备登录验证表单」要求短信二次验证（`LoginForm.vue`）。补全步骤 4-5 后实证通过：设备验证短信发送（需再过一次图形验证码）→ 固定测试验证码 → 完成验证 → `/console/home` → 退出失效。两个实现细节已沉淀通用经验：表单倒计时 `count-on-start` 挂载即空转（60s 内获取按钮禁用、倒计时文案不代表短信已发）；真实发送信号为归零后倒计时文案重新出现。
- **025 前置三次失败的归因（全部闭环，已沉淀 `experience/general.md`）**：①截图 `attachShot` 内 `page.evaluate(document.fonts.ready)` 无超时上限，字体挂起拖到 test timeout——已去除无界预热，改为截图限时+降级跳过（create-product 同款隐患一并修复）；②分支探测 8 秒窗口短于人工过验证码耗时，误判"未触发"——改为长等待二选一（进控制台 or 出现设备验证表单，300s）；③一轮滑块图形验证码人工未通过（「验证失败，请重新尝试」）——人工重试即可，脚本提示文案改为通用表述并放宽等待。
- 022 实证（2026-09-02）：未登录直达受保护页 `/console/home` 被路由守卫重定向登录页（登录面板可见）；未登录直达 `/reset-pw` 经 `meta.auth=false` 公开放行；002 步骤 5 实证已登录回访 `/login` 照常展示、无强制回跳控制台，会话不受影响（随后退出正常失效）。
- 023 实证（2026-09-02）：注册表单协议勾选与提交联动——未勾选时提交按钮禁用（disableLogin 含 `!agreementChk`），勾选后变为可用；与 007（登录表单）形成"同一控件跨表单分别成行"的完整覆盖。
- 原 21 条结论（2026-09-01）：账号密码登录表单、短信验证码登录、手机号长度边界、未勾选协议拦截、无效凭证失败、登录验证码错误；注册表单结构与提交拦截（003 修正）、注册成功、注册验证码错误、同手机号多企业+管理员默认身份（011）、企业标识格式与唯一性（012）、字段级校验矩阵（013）、重复企业名称被后端拒绝（014）、重复信用代码提交被拒（015）全部通过。
- 验证码过期场景列为范围外：需等待验证码有效期（分钟级），不适合快速通道执行。
- 涉及短信、登录态和注册提交的步骤需要人工完成图形验证码，且仅可在用户确认的 test/pre 环境执行。
- 003 步骤 5 断言按实现修正：验证码不在 `disableLogin` 内，验证码为空时提交按钮实际可用，点击后被表单校验"请输入验证码"拦截，不发请求。
- 014 证实后端存在企业名称唯一性校验：重复名称提交返回"已存在"类失败提示（role="alert" 断言），不产生数据记录；2026-09-02 重跑实际文案"该企业名称已存在,请确认是否已注册或更换其他名称"与需求文案一致。
- 012/013 证实三项输入规范化（实现优于需求的报错拦截）：企业标识仅保留小写字母和数字（大写字母等非法字符被自动剔除而非转小写）；信用代码自动剔除 I/O/Z/S/V 并转大写（填入含 I 的内容不报错）；注册手机号有 `mobile()` 格式校验，与登录侧无格式校验形成对照。
- 015/016 证实信用代码唯一性的完整语义：015 双分支——待审核期间提交报"正在申请中"，历史申请审核通过后重跑触发"统一社会信用代码已注册"；016 用第二测试手机号（`TEST_PHONE_SECOND=13000000001`）提交待审核记录的信用代码被"该账号服务正在申请中"拒绝，实证**待审核申请即占用信用代码**（与其他手机号无关，维度是信用代码本身）。2026-09-02 重跑：016 拒绝提示本次渲染为 role="alert" 浮层（前次为无 alert 角色的 toast），同一后端拒绝的提示组件形态在两次运行间不一致，前端提示实现不统一的发现进一步坐实。
- 020 实现差异（2026-09-01，待反馈产品）：注册表单对空值的拦截是"任一必填为空即禁用提交按钮"（RegisterForm disableLogin），清空+失焦无字段级"请输入××"提示（字段提示仅非法值触发，见 013）；与需求"非空校验，不输入提示"的预期口径不同。2026-09-02 重跑行为一致。
- 018 实现差异（2026-09-01）：密码重置表单为链式校验——验证码字段在手机号合法前禁用，全空提交仅手机号出非空提示，非四字段同时提示；各字段错误为行内文本（无 alert role）。
- 注册提交成功以页面进入注册受理状态为可观察信号；成功后将本次生成资料全量明文记录到包内 `runtime/generated-data.json`（测试手机号亦为合成值；`runtime/` 不提交 Git）。本轮注册成功链路（008 执行的 004/005/019）写入一条台账记录，014 即时从台账读取历史名称触发唯一性拒绝，链路闭环。
- 登录失败提示以 `role="alert"` 浮层断言（element-plus message 组件固定渲染该角色，不受主题 namespace 前缀影响）。

## 断言策略说明

- 字段校验类用例采用“行为成立即通过 + 文案差异记录”：断言的是“出现/不出现校验提示”这一行为，实际提示文案与需求文案的差异以“文案差异”注解写入报告（前端调整文案不会误报失败，差异也不会静默丢失）。两条边界：捕获到的提示须再与用例预期终态比对（字段相关性/拒绝语义/跳转 URL），无关提示不作为通过依据；“预期出现提示”的场景未出现才秒级失败，“预期无提示”的场景（013-D09 选填、013-D13 允许类型）以短等待窗口内未出现为通过条件。元素定位仍为 ARIA 语义优先；需求即文案的场景（如字数计数器 10/11）保持精确断言。

## 已知差异与限制

- 新注册企业待审核期间不进入所属企业列表；“一个手机号可以注册多个企业”成立但需串行（等上一笔申请审核完成后再次发起）。注册账号默认管理员身份已由所属企业列表全量断言（企业权限列均为“管理员”，操作列为“转移管理权限”）。
- 企业简介需求为“选填、≤300 字符”，前端实现为 length(10,100)：留空可通过表单校验层（length 跳过空值，提交被验证码必填拦截），非空时须 10-100 字符；maxlength=100 使超长输入以截断呈现，差异已实证。
- 登录手机号前端仅做长度校验（maxlength=11），无格式校验（006 D04 固化）；注册侧有 `mobile()` 格式校验（013 D14），两侧不一致，待产品确认。
- 营业执照上传未拒绝非图片文件（.txt 可通过 upload 校验），是否需要类型限制待产品确认（013 D13）。
- 「获取验证码」按钮的可用性不受用户协议勾选约束；协议约束仅在提交时生效（007）。
- 同手机号短信发送存在频控（2026-08-31 曾单轮第 8 发被拒，具体窗口未知）；用例内已加发送快速失败检测，被拒时秒级报错提示等待窗口重跑（2026-09-02 单轮 8 发全部成功）。**2026-09-10 重测实证：单轮 11 发时第 11 发（025 首次设备验证短信）被拒，提示“操作太频繁，请稍后再试”**——频控阈值在 8-11 发/轮之间且与时间窗相关；固定测试验证码在被拒后仍被设备验证分支接受（test 环境固定码语义），登录终态不受影响。025 脚本已补频控竞速检测（倒计时/拒绝提示谁先出现走谁，拒绝记注记后继续），不再静默空等 240s。需要“全新短信发送”的干净证据时，等频控窗口重置后单独重跑 025。
- 邮箱格式前端校验：`abc@` 触发“请输入正确的邮箱地址”，留空无提示（选填实证，013 D08/D09）。
- 运行报告与失败 trace 位于同包 `artifacts/`，不提交 Git；本文件不记录逐次运行流水。
- 本功能生成数据以增量累积台账形式追加写入同包 `runtime/generated-data.json`（只增不删；含测试手机号，均为合成值），后续用例（012/014/015）从台账读取历史企业标识/名称/信用代码构造重复数据，不复用历史注册账号本身。

## 后续关注

- “注册后使用刚注册账号登录”现已具备前提（已有一条注册审核通过）：可新增明确的串行测试链路和数据依赖说明后补充用例。
- 同一后端拒绝提示（code 10423“正在申请中”）的渲染形态不稳定：不同提交路径下不一致（toast 无 alert 角色 vs role="alert" 浮层），且同一路径在两次运行间也会变化（016 第二手机号路径 2026-09-01 为 toast、2026-09-02 为 alert 浮层）；脚本已按竞速宽匹配兼容两种形态，建议前端统一提示组件，便于用户与自动化一致感知。
- 人工点选图形验证码存在票据有效期：点选耗时过长时提交会报“验证码无效或已过期”，重跑用例即可（脚本已对该场景秒级失败并给指引）。
- 需求未定义登录失败锁定策略；如后续确认存在连续失败锁定，应补充相应用例。
