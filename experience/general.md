# 通用项目经验

## 运行与流程

- 运行命令、地址解析、报告查看与完整流程的权威在 `AGENTS.md`（跑测试/流程固定）与 `docs/FAST-TRACK.md`（运行手册），本文件不重复维护，只记排错教训与实操模式（如本文件后续的 trace 清理、台账保护、点选协作模式）。

## 人工协助点选验证码的协作模式

- 页面强制弹出点选文字等图形验证码时，测试以有头模式运行，并在点击“获取验证码”前用 `console.log` 输出人工提示（说明等待时长）。
- 人工通过的同步信号：验证码按钮进入倒计时文案（如“{N}秒后重新获取”），用 `page.waitForFunction` 轮询 `document.body.innerText` 匹配倒计时正则。
- 人工等待窗口远大于默认超时：该测试必须 `test.setTimeout(360_000)` 级别的独立超时，`waitForFunction` 传 240 秒左右。
- 运行前明确告知用户：浏览器窗口弹出后只完成验证码点选，期间不要关闭窗口。

## 页面结构探索的等价手段

- 探索前先确认所需 MCP（chrome-devtools / playwright）在当前环境可用；不可用时**先询问用户是否需要帮忙安装或接入**（接入口径见 `docs/FAST-TRACK.md`「MCP 接入」），经用户同意降级后才使用下面的无头脚本手段，不得默认跳过 MCP。
- 环境没有 Chrome DevTools MCP 时，用无头 Playwright 脚本（放在 `testpacks/<type>/<project>/<feature>/runtime/exploration/`）对页面做 `page.locator("body").ariaSnapshot()` 与整页截图，产物写入同目录的 `out/` 后阅读分析，效果等价于 MCP 探索。
- 探索脚本只做只读操作（打开页面、快照），不点击写操作按钮。
- 需要凭据的探索：脚本内 `import "dotenv/config"` 直接从 `.env` 读取并填入页面，凭据不经过会话工具参数；确需人工过验证码的探索按上一节协作模式改为有头运行。

- 规则本体在 `skills/testcase-designer/SKILL.md`「工作流——划定范围（七类提取）」，此处不重复规则，只记实操教训。
- 实操教训（2026-09-01 登录注册用例集三次扩充）：仅靠需求文档列用例会系统性遗漏整块功能——密码重置页在需求 docx 里只有一句引用、原型只有脱敏截图，但前端 `ResetPassword.vue` 是完整实现（路由、校验规则、提交跳转俱全）；逐类核对后必须**读前端源码核对实现事实**（路由表、表单校验规则、按钮 `:loading` 防重复、终态页面文案），发现"原型未覆盖但已完整实现"的功能一并纳入。该轮实践里唯一性/字段校验维度已投入 5 条用例仍属充分，但空值非空提示、提交幂等、入口互跳、终态展示被整体遗漏，逐类核对才暴露——遗漏的往往不是"没测好的项"，而是"没列入范围的整块类别"。

## 元素定位与断言的稳定锚点

- 定位优先级的规则本体在 `docs/FAST-TRACK.md`「脚本——定位与断言」（AGENTS.md 只留义务红线）：**有 ARIA 尽量用 ARIA（`getByRole`、可访问名称、`aria-*` 属性），没有再依次降级**为可访问文本、placeholder、项目自有业务类；第三方组件库的内部类名不作定位依据。
- 提示类断言总纲"行为成立即通过 + 文案差异记录"的规则本体在 `docs/FAST-TRACK.md`「脚本——提示类断言」。可复用的实现模式（2026-09-01 OP-AUTH-013/016 沉淀）：`collectVisibleNotices` 动作前收集基线（跑两次取并集防渲染竞态，排除"获取验证码/重新获取"等按钮态文案）→ 动作后 `captureNewNotices` 只捕获新出现提示（250ms 轮询）→ `noteCopy(step, 预期文案, 实际提示列表)` 一致打 `[文案一致]`、差异推"文案差异"注解。提交后多分支判定用单个 `waitForFunction` 竞速（跳转 / role=alert / toast 文案），15 秒无结果立即失败并截图。两条边界（2026-09-01 补充）：竞速/捕获到的任一结果（跳转 / 新 alert / 新 toast）只是捕获而非通过依据，须再与用例预期终态比对（拒绝语义关键词、跳转 URL、字段相关性），无关新提示不得让用例误通过（实现上 noteCopy 记录差异后再做语义 expect 兜底）；"无提示秒级失败"仅适用于预期出现提示的场景，预期无提示的用例（013-D09 选填邮箱、013-D13 允许 txt 类型）以"短等待窗口内未出现相关提示"为通过条件。
- 典型案例：element-plus 的 ElMessage 错误浮层固定渲染 `role="alert"`，用 `getByRole("alert")` 断言。依据：2026-08-31 OP-AUTH-008 排错，`.el-message--error` 与 `[class$="message--error"]` 均落空（本项目 `el-config-provider namespace="ep"`，且命令式 API 的类名前缀与配置、版本相关），改用角色定位一次通过；`role="alert"` 为组件源码固定契约，不随主题前缀漂移。**适用边界（2026-09-01 补充）**：该结论仅适用于确认走 ElMessage 的路径；不同提交路径可能换用无 alert 角色的 toast（见下条竞速捕获），批量拒绝断言一律按 AGENTS.md 提示类断言规则（单次竞速 + 终态校验），不得只押 `getByRole("alert")` 单形态。
- **同一后端拒绝在不同提交路径下提示渲染可能不一致**（2026-09-01 OP-AUTH-015/016 实证）：同样的 code 10423“正在申请中”，主手机号路径弹出 `role="alert"` 浮层、第二手机号路径曾弹出无 alert 角色的 toast（图形票据过期提示同样是无角色 toast）。断言不要只押一种形态：提交后用单个 `waitForFunction`（1 秒轮询）同时竞速捕获“跳转 / role=alert / 任意可见拒绝文案”，宽匹配（申请|占用|重复|已注册|已存在|无效|过期|失败），15 秒无提示立即失败并截图说明——绝不串行等待（先等 A 超时再找 B 必然错过 3 秒生命周期的 toast），也绝不静默空等让操作者无从判断。
- 项目自有的业务类名（如控制台退出入口 `.user-meta-list .btn-usermeta`）已被多次运行验证稳定，属于降级序列中的合法锚点；隐藏控件（如样式化上传的 `input[type="file"]`）无可见 ARIA 目标，属"没有 ARIA 再用别的"的正常情形。
- 组件的 ARIA 语义以装包源码为准（如 `node_modules/element-plus/es/components/message/src/`），页面 aria 快照与源码互相印证后再写入脚本。

## 失败产物的敏感信息清理

- trace 与 error-context 会包含输入值（如手机号）。测试通过时不保留 trace（`retain-on-failure`）；失败运行排错完毕后，清理对应功能测试包 `artifacts/results/` 下目录再重跑，避免敏感输入长期留存。
- **先取证再清理**：删除失败产物前，先把排错所需的证据提取完（元素真实类名/结构、输入值、时序——trace 里通常有逐帧 DOM 快照）。2026-08-31 OP-AUTH-008 排错时先删了 trace，导致 toast 真实类名无法复盘、只能靠改断言方式绕过，多消耗了人工验证码。
- **toast 类短命提示大概率进不了 trace 帧快照**（2026-09-01 OP-AUTH-016 排错）：53 帧 DOM 快照均未捕获 3 秒生命周期的 toast；真正的证据在 trace 的 `0-trace.network`（请求/响应体，业务 code 与 message 全在里面）。排错顺序应是：先看网络响应确认后端行为，再回头调页面断言；网络层证据永远比 UI 层证据可靠且不消失。
- **清理范围仅限 `artifacts/`**（trace、报告、临时截图）；`runtime/generated-data.json` 是增量累积台账（只追加、不删除、不清空），历来用例会从中读取历史企业标识/名称/信用代码构造重复数据，任何清理不得波及。2026-08-31 曾把台账当一次性产物整体删除，导致平台已有 3 家测试企业而台账只剩 2 条记录，历史数据对不上。
