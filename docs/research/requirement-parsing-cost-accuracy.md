# 需求解析的成本-准确率平衡：调研、实测与工程方案

> 状态：方案已批准实施（2026-08-21）。本文档是调研结论与本仓实测基线的唯一事实源；
> 后续请求的成本数据以各运行档案 `cost-report.md`（`npm run cost:analyze`）为准。
> 在线市场调研因搜索配额耗尽未完成，第 2 节案例为模型内置知识并标注「待核实」，
> 配额恢复后应补一轮在线核实并更新该节。

## 1. 问题定义

需求解析（受控需求文档 → REQ 索引 → RULE 台账 → 用例）是每次测试请求的第一段，
也是此前唯一没有计量的段落。用户问题：怎么平衡成本（时间与 token）和准确率（含完整度）。

两类成本、两类准确率：

| 维度 | 度量 | 现状 |
| --- | --- | --- |
| 时间成本 | 活动净耗时、重试/漂移空闲、人工等待 | 可从 `workflow-history.ndjson` 派生（本轮落地） |
| token 成本 | input/output/cacheRead 分会话累计 | 可从 DSH 会话日志逐调用 usage 聚合（本轮落地） |
| 准确率 | 断言忠实于资料、不补造 | reviewer 隔离评审 + converged 二值终止（既有） |
| 完整度 | 资料定义的需求无遗漏 | REQ→RULE→case 闭包（既有）；**行覆盖闭包审计（本轮新增，见 §5.3）** |

## 2. 市场案例调研（内置知识，待在线核实）

> 诚实声明：web_search 当前不可用（Insufficient Balance）。以下结论来自模型训练知识，
> 用于提供方向性参照；逐条核实待配额恢复后补做。

### 2.1 商业测试平台

| 案例（待核实） | 做法 | 对本仓的启示 |
| --- | --- | --- |
| TestRigor | 自然语言→用例，核心是确定性解析而非自由生成 | 结构化中间表示（REQ/RULE 台账）优先于自由文本，本仓已具备 |
| Tricentis Tosca + Copilot | LLM 只做辅助，产物必过人工确认门，风险驱动选择范围 | 对应本仓「用例确认只批准设计」与 speed 档风险分流 |
| Functionize / Mabl / Testim | ML 解析需求 → 生成 → 人工评审收敛 | 收敛靠「生成-评审-确认」环，不靠单次生成质量 |

### 2.2 大厂内部实践（方向性参照）

普遍把需求解析拆三段：**结构化抽取（规则/小模型）→ 测试点发散（大模型）→ 用例编排（模板）**，
人工只审边界与歧义。本仓「冻结骨架 → 并行片段 → 确定性拼装」与该三段式同构，
且多了 reviewer 隔离与 Git 台账两个审计面；差距在抽取段仍由主 Agent 人工转录（§5.3 补齐）。

### 2.3 学术与评测（方向性参照）

LLM 需求→用例的已知短板集中在：**幻觉补造断言**与**漏覆盖**（completeness）。
公认有效的缓解：检索/范围增强、确定性覆盖审计、人工确认门——分别对应本仓的
受控来源选择（manifest sectionId）、本轮新增的行覆盖闭包审计、用例确认 callback。

### 2.4 长文档 LLM 工程

- 查找型任务用 RAG（省 token 但碎片化上下文）；**一致性/交叉对照任务用 scoped 全文**
  ——需求解析属后者，平行需求段交叉对照（红线 5）不可用碎片检索替代。
- 前缀缓存（DeepSeek/GLM/Anthropic 系，cache 命中价约为原价 1/10）是零准确率损失的降本：
  稳定前缀（项目约定+冻结骨架）在前、易变内容在后。本仓 §5.4 落地为 prompt 结构约定。

> ² 跨夜等待 18.4h，时间窗混入并发会话，token 口径为上界。

### 3.2 关键发现：主会话是 token 大头，不是 reviewer

registration-review-20260821 分会话拆解（占总 cacheRead 33.70M）：

| 会话角色 | 调用 | input | output | cacheRead | cacheRead 占比 |
| --- | --- | --- | --- | --- | --- |
| 主会话（骨架/编排/对账） | 198 | 395,699 | 108,750 | 29,964,864 | **89.0%** |
| 收尾交付会话 | 30 | 52,721 | 19,393 | 3,232,896 | 9.6% |
| 4 个片段子代理合计 | 8 | 90,023 | 51,482 | 173,888 | 0.5% |
| reviewer r1 + r2 合计 | 9 | 74,093 | 33,051 | 328,576 | 1.0% |

结论（改写优先级）：

1. **长主会话每调用重读累积上下文是最大 token 成本**（198 次 × 平均 ~150K cacheRead）。
   架构方向「能下沉到子代理的就下沉」已被数据证实——片段+reviewer 全部加起来只占 1.5%。
2. **时间成本的大头是重试/漂移空闲与串行预工作**，不是评审本身（r1 6.9min + r2 3.7min）。
   租约合并链经验已沉淀（MEMORY.md EXP-8930A9E44C21）。
3. reviewer 输入瘦身（P2）优化的是 1% 量级的切片，价值在于**可扩展性**（大需求文档时代价线性上升）
   而非当期节省；准确率护栏（读取图强制交叉对照标记）是其附带收益。

## 4. 平衡框架（决策规则）

- **不可交易项（准确率红线）**：REQ 覆盖闭包、平行需求段交叉对照、边界/状态机红线、
  reviewer 只读隔离、converged 二值终止、评审快照/纪元契约（源文件全文 digest）。
- **可交易项（成本旋钮）**：读取广度、prompt 缓存对齐、确定性预提取深度、（远期）模型档位路由。
- **四条规则**：①无计量不动旋钮；②脚本能算的不让 LLM 转录；③默认定向读取、
  交叉对照与存疑回退全文；④发现率/覆盖审计劣化即回退全量上下文。

## 5. 工程落地

### 5.1 计量层（已落地）

`npm run cost:analyze -- --request <id>`：时间口径（活动净耗时/空闲/漂移、reviewer 批次、
人工等待）+ token 口径（DSH 会话逐调用 usage，去重口径=仅 `assistant/message`）。
纯函数在 `src/support/task-workflow/requestCostAnalysis.ts`，单测 8 项；
报告落 `.local/test-runs/<req>/cost-report.md`（gitignored，只含数字与掩码标签）。

### 5.2 reviewer 定向读取图（P2）

`scripts/build-review-reading-map.ts`：从套件 design.md 的 RULE sourceRef 行号引用确定性推导
reviewer 各角色的读取图——引用行区间并集、平行段配对标记、全文回退条件。
规范修订：reviewer 输入文件集不变（快照契约不动），按读取图定向读取。

### 5.3 需求事实预提取 + 行覆盖闭包审计（P3）

`scripts/preflight-requirement-facts.ts`：对受控源做行级确定性抽取（上限/下限/必填/格式/分页/
排序/枚举句式），产出「原文逐字引用+行号」候选表，主 Agent 从转录者变为校对者；
同一脚本计算 scope 内已引用行区间并集与未覆盖区间清单——未覆盖区间必须在 design.md
显式登记不适用/排除，漏覆盖从「信任模型读全了」变成机判。

### 5.4 缓存对齐（P4）

片段/reviewer prompt 结构约定：稳定前缀（项目约定+冻结骨架头字节）在前、易变内容在后，
命中 provider 前缀缓存；以 cacheReadTokens 增量验证。

## 6. 验证与回退

真实效验证挂下一个测试请求（不伪造）：reviewer 输入 token 降幅、≤2 批次收敛、
行覆盖闭包零未登记缺口；任一不达标按 §4 规则④回退全量上下文并复盘。
