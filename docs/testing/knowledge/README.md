# 项目测试经验库

<!-- owns: automation.project-knowledge -->

本目录保存纳入 Git 的**项目测试经验**。每个被测项目独立维护一个 `<project>-testing-knowledge.md` 文件，避免将开放平台、App、MQTT 或其他项目的经验混用。

它与 `sources/knowledge-base/` 的原始知识资料库职责不同：原始资料库保存可追溯的业务事实和原文；本目录记录已经形成、可供后续复核的项目测试策略，未完成验证时明确标记为“待验证”。两者冲突、原始资料版本变化或证据不足时，以当前测试请求在 `plan.md` 中确认的原始资料和结论为准。

## 使用规则（唯一责任源）

- 任务开始时，先由用户测试需求确认被测项目，再读取当前项目对应的知识文件；用户长期协作偏好仍读取 `.local/testing-memory.md`。代码仓库定位属于用例确认后的工程层，不用于替代项目确认。
- 项目经验与工程经验分工：`<project>-testing-knowledge.md` 只记录**被测产品**的产品测试经验（环境约束、定位策略、失败归因、被测系统行为）；测试工程自身（工作流引擎、用例文档契约、评审编排、套件复用、工具链）的经验一律写入 [MEMORY.md](./MEMORY.md)，不落入任何被测项目文件。判定标准：该经验换一个被测项目是否仍然成立——成立即工程经验。完整的沉淀规则（写入判据、范围、证据要求、状态生命周期）见 MEMORY.md 开头的「经验沉淀规则」节。
- 项目测试经验记录可复用的流程、环境约束、恢复策略、失败归因、定位或脱敏策略。策略形成时立即写入并标记“待验证”；取得证据后更新为对应的已验证状态。不得复制需求正文、协议字段说明、接口契约或产品规则；此类事实应保留在 `sources/` 并通过 `manifest.yaml` 追溯。
- 同一“项目 + 适用范围”只保留一条当前策略。出现新观察或策略冲突时，最新可审查记录必须按适用范围原位覆盖旧记录；旧内容仅由 Git 历史保留，不在正文并列两个相互冲突的“当前”结论。
- 每条经验固定采用“适用范围 → 证据状态 → 观察 → 判断 → 当前优先策略 → 证据引用 → 验证条件 → 最近更新”。该结构吸收成熟决策记录中的上下文、依据、决定、状态和复核条件，但继续使用本仓库的单条原位覆盖与 Git 留痕方式。观察来自原始资料时只记录对应 manifest `id`，不复制原文。条目格式与锚点契约以 `src/support/project-knowledge/projectExperienceStore.ts` 为准；标题与“适用范围”字段必须使用同一 scope，证据状态仅允许 `待验证 / 受控探索已验证 / 正式执行已验证`。
- `.local/project-knowledge-candidates/<project>.json` 只保存候选编号、验证状态和经验库引用等控制元数据。候选形成时，`candidate-add` 必须在同一次操作中把正文写入本目录并标记“待验证”；计划仍只引用 `CAND-<编号>`，不得复制候选正文。验证完成后原位更新同一经验的证据状态和引用，并把候选标记为“已提升”。报告阶段只复盘验证、覆盖、放弃和剩余候选。资料明确的手机号格式、验证码阈值、OAuth 分支等需求事实仍保留在 `sources/` 和 `REQ → RULE → caseId`，不属于项目经验。
- 生产访问、业务写入、上传、OTP、安全挑战、权限和设备动作等授权决定按请求单独确认，不得沉淀为可跨请求复用的项目经验。
- 严禁记录账号、密码、验证码、Cookie、Token、密钥、完整生产地址、设备唯一标识、真实用户信息或敏感业务数据。
