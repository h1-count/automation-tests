# 自动化测试失败分类规范

## 1. 目的与适用范围

本文定义自动化测试执行失败的分类、证据要求和处理流程，适用于 Web、App、API、MQTT 和 IoT 链路测试。

分类的目标是帮助团队快速决定后续动作，而不是在证据不足时猜测责任方。项目报告规范见 [report-guideline.md](./report-guideline.md)，项目强制规则以 [AGENTS.md](../../AGENTS.md) 为准。

## 2. 分类原则

- 每个非通过终态必须有一个受控主分类及其依据；必要时可记录次分类或关联因素。脚本不得写入自由分类字符串。
- 主分类只基于已保存的证据、已确认用例预期和已验证前置条件得出。
- 证据不足、无法稳定复现或多个分类无法区分时，使用“未知问题”，不得强行归为产品问题。
- 同一现象可能先被标记为环境、数据或未知问题；补充证据后允许调整分类，并保留调整原因。
- “不稳定（flaky）”是执行特征，不是主分类；必须同时记录其当次的主分类。
- 正式 Runner 只按受控状态与证据派生结构化主分类，脚本、CLI 和主 Agent 都不能人工填写或覆盖；用户或测试负责人审核的是缺陷归属与后续处理。若分类依据后来被证明错误，应保留原封印记录并建立新的受控执行，不能改写历史结果。

## 3. 分类总览

| 主分类 | 分类代码 | 定义 | 首选处理方 |
| --- | --- | --- | --- |
| 产品问题 | `PRODUCT` | 已确认预期、环境、数据和脚本前提满足，但实际产品行为不符合预期。 | 产品 / 研发 |
| 脚本问题 | `SCRIPT` | 产品行为或接口符合预期，但测试实现、定位、等待、断言或清理逻辑不正确。 | 测试开发 |
| 环境问题 | `ENVIRONMENT` | 服务、网络、部署、认证、设备、Appium、Broker 或外部依赖不可用或异常。 | 环境 / 运维 / 相关研发 |
| 测试数据问题 | `TEST_DATA` | 账号、权限、设备、前置数据、数据隔离、清理或数据状态不符合用例要求。 | 测试数据负责人 / 测试开发 |
| 基础设施问题 | `INFRASTRUCTURE` | Runner、worker、Capability Provider、制品或测试框架在业务观察边界外失败。 | 测试平台 / 基础设施负责人 |
| 未知问题 | `UNKNOWN` | 当前证据不足，或无法可靠区分上述分类。 | 测试负责人组织排查 |

用例状态与主分类是两个维度：`failed` 只允许对应已证明的 `PRODUCT / business_oracle_violated`；已证明的环境或数据前置不满足为 `blocked`；脚本、基础设施、观察歧义、中断或无法定案的业务结果为 terminal `unknown`。已知根因可以使用 `SCRIPT` / `INFRASTRUCTURE` 等受控分类，但不能因根因已知就把未定案业务结果改成产品失败。

## 4. 分类决策流程

```text
测试是否实际启动并到达目标系统？
  ├─ 否：检查网络、服务、认证、设备、Appium、Broker → ENVIRONMENT
  └─ 是
      ↓
测试账号、设备、前置数据和权限是否满足已确认用例？
  ├─ 否 → TEST_DATA
  └─ 是
      ↓
脚本是否使用正确 selector、等待、请求、断言和清理逻辑？
  ├─ 否，且产品行为满足预期 → SCRIPT
  └─ 是或无法确认
      ↓
实际产品行为是否违反已确认预期？
  ├─ 是 → PRODUCT
  └─ 证据不足或无法稳定复现 → UNKNOWN
```

当多个分支同时成立时，优先标记最早阻断执行的原因，并把其他因素记录为次分类或待确认项。例如 Broker 不可用导致页面未展示告警，应先标记 `ENVIRONMENT`，而不是直接标记页面产品问题。Runner 或 Provider 本身失败使业务 Oracle 无法求值时，case 保持 `unknown`，主分类为 `INFRASTRUCTURE`。

## 5. 产品问题（PRODUCT）

### 判定条件

- 测试计划、用例、目标环境和预期已确认。
- 环境服务、账号、设备和测试数据均满足前置条件。
- 脚本的 selector、请求、等待和断言已验证正确。
- 已绑定当前 `RULE` 与受控来源的业务 Oracle 返回 `violated`。没有该结构化结果时不得使用 `PRODUCT`。

### 常见信号

- 合法参数提交后接口返回不符合契约的错误码或字段。
- 页面或 App 未展示应出现的业务状态、告警或权限入口。
- 状态流转、数据一致性或业务规则与确认用例不一致。

### 最小证据

- `caseId`、目标环境、前置条件和预期结果。
- 最小复现步骤、时间范围和测试数据别名。
- 页面截图/Trace，或 API/MQTT 的脱敏请求响应摘要。
- 已排除环境、数据和脚本问题的依据。

### 后续动作

创建缺陷或通知研发，附最小复现、证据路径、影响范围和建议优先级；不要在脚本中放宽断言来掩盖产品问题。

## 6. 脚本问题（SCRIPT）

### 判定条件

- 产品功能可通过人工验证、稳定 selector、正确请求或其他独立证据证明符合预期。
- 失败由 selector、等待、断言、请求拼装、context 切换、fixture、清理或脚本逻辑引起。

### 常见信号

- 页面元素存在，但 selector 失效、匹配多个元素或依赖动态 class/位置。
- 页面异步加载尚未完成，脚本使用固定等待或过早断言。
- App WebView 未切换 context，或 API 请求参数/签名由脚本拼装错误。
- 测试数据已创建成功，但清理脚本误删或误判结果。

### 最小证据

- 失败脚本片段、错误摘要和关联 `caseId`。
- 截图、Trace、DOM/可访问性树或 Appium Inspector 信息。
- 证明产品实际行为符合预期的独立证据。

### 后续动作

输出最小脚本修复 diff、影响用例、验证命令和风险；用户审核后再修改和复测。禁止用坐标点击或扩大 XPath 作为默认修复方式。

## 7. 环境问题（ENVIRONMENT）

### 判定条件

环境、基础设施或外部依赖无法支持已确认测试执行，包括网络、服务、部署、认证服务、设备连通、Appium、Broker、数据库或第三方服务。

### 常见信号

- 页面、API 或 Broker 无法连接，出现 DNS、超时、5xx、TLS 或网络错误。
- 登录服务、依赖服务或测试环境部署异常。
- 模拟器/真机离线、Appium Server 不可用、WebView context 无法获取。
- MQTT Broker 连接失败、订阅无权限或消息无法消费/入库。

### 最小证据

- 目标环境、执行时间、命令和失败错误摘要。
- 健康检查结果、服务状态或网络/Appium/Broker 连接证据。
- 证明同一账号/数据在其他可用环境或恢复后可执行的证据（如有）。

### 后续动作

暂停同类受影响测试，通知环境负责人或相关研发；环境恢复后先运行健康检查和最小冒烟用例，再决定是否全量复测。

## 8. 基础设施问题（INFRASTRUCTURE）

### 判定条件

Runner、worker、Capability Provider、证据写入、封印生成或测试框架在业务观察边界外失败，且有结构化错误证明故障属于执行基础设施。

### 常见信号

- BrowserServer、worker 或正式 adapter 异常退出。
- 已登记 Provider 的调用实现失败，而非业务服务返回已定义错误。
- 正式记录、制品或封印读写失败，使当次业务结果不能可靠持久化。

### 最小证据

- 受影响 `caseId`、Runner/Provider 组件和已脱敏错误摘要。
- 证明错误发生在业务 Oracle 定案前或结果持久化边界的时序证据。
- 若已得到产品结果，必须单独保留该结果，不得用基础设施失败覆盖。

### 后续动作

修复执行基础设施并通过定向自测后，只对尚未可靠定案的 case 走受控恢复。不得用普通重试覆盖可能已发生的业务写入。

## 9. 测试数据问题（TEST_DATA）

### 判定条件

测试账号、权限、设备、业务前置数据、数据隔离或清理状态不符合已确认用例的前置条件。

### 常见信号

- 测试账号无所需角色、租户或产品管理权限。
- 测试设备不存在、被占用、未绑定、离线或状态残留。
- 产品名称重复、告警规则未启用、测试数据未清理或并发执行相互污染。
- 使用了真实用户、真实设备或错误环境的数据。

### 最小证据

- 已确认用例的前置条件与实际数据状态对比。
- 脱敏后的账号角色、设备别名、数据标识和准备/清理日志。
- 数据隔离、并发冲突或清理失败的证据。

### 后续动作

修复 fixture、数据准备或清理逻辑，重新准备隔离数据后复测。若无法安全清理或会影响真实业务，升级为审批事项，不得自动重试。

## 10. 未知问题（UNKNOWN）

### 使用条件

- 缺少截图、Trace、日志、请求响应或 MQTT 证据。
- 问题无法稳定复现，或重试结果不一致但尚无原因。
- 产品、脚本、环境和测试数据都无法被充分排除或确认。

### 必填信息

- 已知现象、发生频率、受影响环境和用例。
- 已收集证据及其缺口。
- 已排除的因素与排除依据。
- 下一步最小排查动作，例如补充 Trace、增加脱敏日志、检查 Broker 消费或复测。

### 后续动作

保持 `UNKNOWN`，补充观测与最小复现，不得直接创建产品缺陷或修改业务断言。

## 11. 不稳定用例（Flaky）标记

当同一已确认用例在相同脚本、环境和数据策略下多次执行出现间歇性通过/失败时，可附加 `flaky` 标记。

- `flaky` 不能替代主分类；每次失败仍需记录 `PRODUCT`、`SCRIPT`、`ENVIRONMENT`、`TEST_DATA`、`INFRASTRUCTURE` 或 `UNKNOWN`。
- 标记前至少记录执行次数、通过/失败次数、时间分布和关联证据。
- `flaky` 用例不得静默忽略；应降低回归可信度、建立修复项并在修复后取消标记。

## 12. 分类记录模板

失败分类使用中文 Markdown 信息卡，固定标题如下：

```text
# 失败分析：<用例编号>

## 基本信息
| 项目 | 内容 |
| --- | --- |
| 执行结果 | 失败 / 阻塞 / 未知 |
| 主分类 | 产品问题 / 脚本问题 / 环境问题 / 测试数据问题 / 基础设施问题 / 未知问题 |
| 次要因素 | 无 / ... |
| 置信度 | 高 / 中 / 低 |

## 实际现象

## 预期结果

## 证据
| 类型 | 路径或摘要 |
| --- | --- |

## 已排除因素

## 建议动作

## 待审核事项
```

## 13. 审核清单

- 主分类是否有足够证据，且与已确认用例预期一致。
- 是否把环境、数据或脚本失败误归为产品问题。
- 是否记录了证据路径、置信度、已排除因素和下一步动作。
- 是否对敏感信息、真实设备和生产操作进行了脱敏与审批控制。
- `flaky` 是否作为附加特征而非失败分类使用。
- 修复建议是否保持最小变更，并等待用户审核后实施。
