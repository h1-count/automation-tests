# 结构化测试用例规范

<!-- owns: automation.testcases -->

## 1. 目的与适用范围

本文规范 Web、H5、App、API、MQTT 和 IoT 链路测试用例的编写、审核和维护方式。

测试用例是业务层中已确认测试计划与工程层自动化设计之间的契约：它描述验证什么、在什么环境验证、依赖什么数据、预期什么结果，但不直接包含账号密码、Token、设备密钥、代码路径、selector 或实现细节。用例的原子性由稳定用例编号和可独立报告的预期决定，不由 Markdown 文件数量决定。

项目强制规则以 [AGENTS.md](../../AGENTS.md) 为准；整体阶段流程见 [automation-guideline.md](./automation-guideline.md)。本文是测试设计、追溯模型、用例集评审和变更影响的唯一正文来源。

## 2. 前置条件与状态流转

只有绑定当前 `plan-confirmation-subject-v2` 的计划确认 callback 为 `accepted`，且 `plan.md` 已保存对应正式用户决定后，才能创建正式测试用例草案；计划本身不维护独立状态字段。该确认在顶层业务范围、测试类型与目标环境、高层数据写入类别和权限/安全上限不变时持续有效，后续 `REQ/RULE/caseId`、断言、追溯和 reviewer 记录的证据驱动演进不构成再次确认计划的理由。测试用例按以下状态流转：

```text
草案 → 已确认 → 已废弃
          ↓
       退回修改（回到草案）
```

| 状态 | 含义 | 可否生成正式脚本 |
| --- | --- | --- |
| 草案 | AI 测试 Agent 或测试人员生成的待审核用例，可能包含假设或缺失信息。 | 否 |
| 已确认 | 用户或测试负责人已确认范围、环境、预期和风险。 | 是 |
| 已废弃 | 不再执行；应保留原因和替代用例信息。 | 否 |

Markdown 测试资产中的业务状态统一使用上表中文值，不使用 `draft`、`confirmed` 或 `deprecated` 作为“状态”字段值。该字段是正式用户决定的派生元数据，不是另一份确认事实：`草案 → 已确认` 只能由绑定当前用例集 digest 的有效 callback 和 `plan.md` 正式决定驱动，并通过产物发布事务刷新；作者不得手工推进。只有脚本、接口或测试管理平台确实要求机器字段时，才可额外使用 `statusCode`，并固定映射为：`草案 → draft`、`已确认 → confirmed`、`已废弃 → deprecated`；`statusCode` 不是人工审核状态的替代字段，必须与中文“状态”一致。

### 2.1 测试资产选择记录

`plan.md` 的“测试资产选择”只记录静态候选资产，不是需求追溯或用例来源。App 包、固件或视觉基准未选择、完整性不一致、Appium 未配置或设备不可用时，只能让相应工程设计或执行 Activity 保持未就绪，或在真实解除条件存在时追加 `BlockerRaised`。不得在计划中写任务状态、阻塞已确认范围的用例生成或据此减少业务覆盖。

## 3. 存放位置与命名

测试资产采用“项目 → 测试请求（测试套件）→ 用例包 → 原子用例 → 测试运行”的分层模型。前四层以业务层资产为主；同一测试请求的 `plan.md` 在用例确认后补充工程层设计；测试运行由治理线保存为不可变证据：

- **项目**：按产品或平台隔离测试资产、权限和运行历史。
- **测试请求（测试套件）**：一次独立、可审核的业务主题，承载计划、追溯和用例集评审。
- **用例包**：同一业务模块或完整流程的 Markdown 文档，只负责组织原子用例。
- **原子用例**：具有稳定用例编号、可独立执行和报告的最小业务规则或风险单元。
- **测试运行**：一次执行的结果快照；记录在 `artifacts/`，不改写用例定义。

测试用例使用中文 Markdown，按“测试类型 → 被测项目 → 独立测试请求”保存：

```text
testcases/
├── web/<project>/<test-request>/        # Web 管理后台、独立 H5
├── app/<project>/<test-request>/        # 原生 App、App 内 WebView
├── api/<project>/<test-request>/        # 服务接口
└── iot-chain/<project>/<test-request>/  # API、MQTT、Web/App 组合链路
    ├── plan.md                          # 本次测试请求的已确认测试计划
    ├── cases-<module-a>.md               # 按模块聚合的用例包
    ├── cases-<module-b>.md
    └── ...
```

- `<project>` 和 `<test-request>` 使用稳定的 kebab-case 名称。`<test-request>` 表示一次独立、可审核的测试需求或测试主题，不是一次具体执行或单条用例。
- `plan.md` 负责范围、覆盖基准与拆分清单、需求追溯矩阵、规则覆盖台账、覆盖矩阵、用例包目录、用例集评审结论，以及用例确认后补充的“工程层：代码定位与自动化设计”区块；它不承载完整测试步骤或执行结果。
- 工程层区块记录 `caseId` 与代码/图谱/脚本实现的映射、可行性、数据和风险，不得改写已确认用例的业务规则，也不得另建平行说明文档。
- 用例包命名为 `cases-<module>.md`，按稳定业务模块或完整流程组织，禁止按正向/负向、边界/异常等覆盖维度拆包。
- 常规用例包建议包含 3–10 条原子用例；高风险、独立审批、独立测试数据、跨端链路或需要独立报告的用例可单独成包。该建议用于控制可读性，不作为硬性文件数限制。
- 用例包内每条原子用例使用二级标题，且完整保留第 4 节的必填字段、前置条件、步骤、预期、覆盖关联、`assumptions` 和 `missingInfo`。同一用例编号不得出现在多个用例包中。
- 测试计划、用例包和原子用例必须以真实 Markdown 换行写入；禁止把反斜杠加字母 n 或 r 的转义序列作为正文换行。每张 Markdown 表格的表头、分隔行及每条数据行必须保持相同列数；单元格内需要换行时使用 `<br>`，字面量竖线写为反斜杠加竖线。每次写入或批量更新后，必须先对实际文件运行 `npm run check:markdown -- <文件路径>`，再运行 `npm run check:architecture`；分隔行列数错误只可用 `npm run check:markdown -- --fix <文件路径>` 作确定性修复，数据行错误必须修订生成正文后复检。两项检查均通过前，不得向用户展示为计划/草案或请求确认。
- 需求追溯矩阵、脚本与运行报告只关联稳定用例编号，不依赖用例包路径；移动、拆分或聚合用例包时不得改变用例编号或中断追溯。
- 不同测试请求必须使用不同目录。一个请求发生复测、补充用例或报告更新时，仍归入原请求目录；范围发生实质变化且需重新确认时，建立新的测试请求目录。
- 需要从零开始重新测试且不能让历史草案影响新设计时，将旧请求移动到 `testcases/archive/<test-type>/<project>/<test-request>-archived-<YYYYMMDD-HHmmss>/`。归档请求只读、默认不参与上下文加载，只保留计划、用例包、正式评审、workflow history，以及对应 `automation/` 下的请求专属脚本。未清理或结果未知的外部资源台账不得随请求归档；完整重置必须先失败，待资源恢复或形成明确的 `retained` / `quarantined` 残留决定后再继续。新请求必须重新建立需求基线、范围、环境、`caseId` 和用例确认，不得把归档用例直接恢复为“已确认”。
- 跨项目通用测试设计可放在对应测试类型的 `shared/<test-request>/` 下。
- 既有平铺目录中的草案可在同一测试请求内聚合为用例包；迁移必须保留用例编号、状态、追溯、风险和全部测试内容。已确认用例不得仅为整理而迁移；需要迁移时先获得用户确认并在计划中记录迁移结果。

文件名使用小写 kebab-case，并表达业务能力，例如：

```text
testcases/web/<project>/<test-request>/plan.md
testcases/web/<project>/<test-request>/cases-<module>.md
testcases/app/<project>/<test-request>/plan.md
testcases/iot-chain/<project>/<test-request>/cases-<module>.md
```

“用例编号”使用大写连字符命名，推荐格式为：

```text
<系统>-<模块>-<序号>
```

示例：`OPEN-PLATFORM-PRODUCT-001`、`IOT-ALARM-001`。同一用例编号一经使用不得复用；需求变更导致原用例失效时，将其标记为“已废弃”并新建用例。

## 4. 必填字段

| 信息项 | 说明 | 要求 |
| --- | --- | --- |
| 用例编号 | 用例唯一标识。 | 原子用例文件中的身份来源；全局唯一、稳定、不可复用。 |
| 需求追溯编号 | 对应计划中需求追溯矩阵的编号。 | 至少关联一项；跨需求用逗号分隔。 |
| 规则覆盖编号 | 对应计划中规则覆盖台账的 `RULE-` 编号。 | 由 `RULE → caseId` 关系源同步生成；不得手工回填。 |
| 标题 | 用例标题。 | 描述业务动作与预期结果，不写实现细节。 |
| 模块 | 所属业务模块。 | 使用稳定模块名，例如 `product-management`。 |
| 优先级 | 优先级。 | `P0`、`P1` 或 `P2`。 |
| 测试类型 | 主测试类型。 | Web、App、API、MQTT 或 IoT 链路。 |
| 状态 | 用例状态。 | 草案、已确认或已废弃。 |
| 目标环境 | 已确认执行环境。 | `test`、`pre` 或 `prod`；生产需额外审批。 |
| 来源 | 主要资料来源。 | 包含来源类型、路径或 URL、版本。 |
| 前置条件 | 执行前条件。 | 账号、数据、设备、规则和环境状态必须可检查。 |
| 操作步骤 | 测试步骤。 | 每步有动作、必要输入和局部预期。 |
| 预期结果 | 最终预期结果。 | 可观察、可断言、无模糊措辞。 |
| 自动化状态 | 自动化范围和可执行性。 | 说明涉及域及是否可执行。 |
| 风险等级 | 风险与确认要求。 | 明确风险等级和是否需要确认。 |
| 合理推断 | 未确认的推断。 | 有推断时必须记录依据。 |
| 待补充信息 | 缺失信息。 | 记录影响和待确认项。 |

## 5. 字段编写规则

### 5.1 优先级

| 优先级 | 适用场景 |
| --- | --- |
| `P0` | 核心主链路、关键权限、资金/设备安全、发布阻断风险。 |
| `P1` | 重要业务分支、主要异常处理、常用配置与状态流转。 |
| `P2` | 次要交互、边缘场景、低频功能和体验优化。 |

### 5.2 环境与资料来源

- “目标环境”只能填写已确认的环境，不能根据 URL 或名称自行确定。
- 环境候选项和选择依据属于测试计划，不写入正式用例。
- “来源”使用可点击的仓库相对 Markdown 链接或 URL；只列实际用于该用例规则、步骤或预期的资料，并与 `plan.md` 的“输入资料”实际引用清单一致。每个引用保留 `manifest id / sectionId` 与页码、标题或原型页面定位；章节索引命中、目录扫描或未打开的候选资料不得写入来源。对话附件尚未落盘时标注“仅对话附件，暂无持久链接”，资料不完整时在“合理推断”和“待补充信息”中说明。
- 测试用例中不得写入密码、Token、密钥、真实手机号或个人数据。

### 5.3 前置条件、步骤与预期

- 前置条件必须是可验证或可准备的事实，例如“测试账号具有产品管理权限”。
- 步骤使用业务动作描述，例如“提交创建产品表单”；不写“点击坐标 (120, 320)”。
- “输入”仅记录非敏感测试数据、数据类型或占位符；真实值由 fixture、环境变量或测试数据脚本提供。
- 原子用例必须声明按 [environment-guideline.md](./environment-guideline.md) 选择的数据策略，并引用相应的数据准备或清理安排；不在用例规范重复定义台账、复用和清理协议。
- 每一步的“预期”描述该步骤的即时结果；“预期结果”标题描述最终业务结果和必要的数据一致性结果。
- 禁止使用“页面正常”“操作成功”“符合预期”等无法断言的表述。

### 5.4 自动化可执行性

“自动化状态”填写实际涉及的域，例如 Web、API、MQTT、App，以及可执行性。判断规则：

| 条件 | 自动化状态 |
| --- | --- |
| 用例未确认，或关键资料/环境/数据缺失 | 暂不可执行 |
| 用例已确认，尚未完成 `plan.md` 工程层代码定位与可行性评审 | 待工程设计 |
| 已确认，但尚未具备稳定 selector、测试账号或设备 | 暂不可执行 |
| 已确认，且 `plan.md` 工程层设计已确认脚本前置条件均满足 | 可执行 |

“待工程设计”不表示业务用例缺失；“可执行”不表示可以跳过脚本审核和执行审批。代码与用例预期不一致时，必须回到计划/用例评审，不得以当前实现改写用例。

### 5.5 用例生成前的覆盖基准与拆分

测试计划确认后、生成用例草案前，必须在同一 `plan.md` 的“覆盖基准与拆分清单”完成需求拆分；它是用例生成和评审的检查清单，不是新的说明文档，也不是用例数量 KPI。计划阶段只识别业务规则、风险、场景和用例包边界，**不得预分配、承诺或以数量配额限制最终 `caseId`**；稳定编号只在阶段二原子用例实际生成时分配。清单至少识别：

- 需求模块与主成功、失败、回退、重试等适用业务流程；核心流程应覆盖适用的分支和恢复路径。
- 输入字段及其必填、类型、格式、长度、范围、关联约束和触发动作；仅针对需求或风险适用的维度选择等价类、边界值和异常输入。
- 枚举、数据态、状态迁移、等级、Tab、视图或规则分支；语义、业务规则、状态转换或预期结果不同的项必须能由独立 `caseId` 判定。
- 入口、跳转、弹窗、确认/取消、返回、保存、删除、授权等关键交互；仅因出现关键词不强制新增用例，必须以实际业务风险和可验证结果判断。
- 角色、动作和资源的权限关系；适用权限点至少覆盖允许路径与越权拦截，角色或规则缺失时记录 `missingInfo`，不得猜测默认权限。

若资料中存在 `.xmind` 或用户指定人工用例基准，必须先读取其模块层级与场景范围，并在同一清单中记录 L1/L2、必要时 L3 的映射、计划覆盖范围和缺口原因。阶段二维护关联 `RULE-`，再由同步工具生成实际 `caseId`。XMind 仅用于识别覆盖缺口：不得一对一照搬正文，不设固定数量或百分比配额，也不得以汇总用例掩盖具有不同可观察预期的场景。

原子用例以可验证的业务规则或风险为最小单位，而非页面控件数。相同规则的等价输入可以组织在同一可独立报告的场景中；不同失败原因、状态迁移、权限结论或预期结果必须拆分为可独立报告的用例。主流程可使用完整链路步骤；单点场景仍须包含足以复现和断言的前置条件、操作和预期，不得为增加数量而重复描述。

使用当前测试计划模板创建或变更的请求，保留模板中的“结构版本：coverage-inventory-v1”行；`npm run check:architecture` 会对此类请求严格校验清单和原子用例关联。旧 HTML 注释标记的存量请求按兼容模式识别，不要求为本次规范更新而迁移；其后续变更时应补充可读结构版本行。

#### 规则设计矩阵与严格预检

初始用例生成前，必须在同一 `plan.md` 增加从已引用 `RULE` 派生的“规则设计矩阵”，并保留“结构版本：rule-design-matrix-v1”。它不是第二份需求来源：每行只解释已引用规则如何被设计、验证和受控执行。每条适用或受控执行的 `RULE` 必须记录字段或状态对象、必填/选填结论、有效/无效/边界输入、可观察预期、数据前置、执行门禁与“已覆盖 / 受控执行 / 用户裁决 / 不适用”结论；其中“关联 `caseId`”只能由规则覆盖台账的唯一关系源同步生成，不得在矩阵中人工维护。

资料未定义格式、文件属性、成功页或恢复语义时，矩阵必须明确写“不生成断言”及资料定位；不得用“已定义校验”或泛化描述替代。生成、补齐或演进用例后，先对 runtime 暂存副本运行 `npm run testcases:sync-relations -- <暂存请求目录>`，再对暂存的 `plan.md` 运行 `npm run check:rule-design -- <暂存 plan.md>`；全部通过后由对应 Activity 原子发布。预检发现的普通遗漏必须自动修订草案、同步 `REQ → RULE → caseId` 并复检，不启动 reviewer，也不向用户索取普通修订许可。

每次评审发现映射到某一 `RULE` 后，自动演进必须复核该规则邻域：同一 `REQ`、同一字段或状态对象、同一提交/状态路径或同一数据前置组的全部适用规则。计划的“规则邻域复核”记录触发发现项、邻域 `RULE`、共同依据、修订 `caseId` 和复检结果；资料明确的邻域遗漏一次性自动修订。只有资料冲突或未定义验收才保留为用户裁决。

#### 正式业务 Oracle 契约

新建的正式执行清单使用 `formal-execution-manifest-v3`。每个 runnable `caseId` 至少声明一个业务 Oracle，且每个 Oracle 只能绑定当前 case 的一条 `RULE`。Oracle 的可观察预期从 `plan.md` 的规则设计矩阵派生，不得在 manifest 再复制一份自由文本预期。每个绑定必须形成 `REQ → RULE → caseId → oracleId` 的唯一链路；缺失、重复、孤立或跨 case 绑定都是 build 错误。

Oracle 权威依据只允许两类：一是 `sources/manifest.yaml` 中 active 且适用当前项目、已由 reviewed knowledge index 登记的材料章节；二是 `plan.md` 中已接受的正式用户决定。材料路径、章节、项目适用性、实际文件 SHA-256、索引和用例包回链必须一致；代码、Graphify、selector 或运行截图只能证明实现可行性，不能作为业务预期来源。

正式用户决定作为 Oracle 权威依据时，`plan.md` 必须使用以下固定表头；`subjectDigest` 是被裁决主题的 SHA-256，不是决定正文摘要。只有“正式决定”为 `accepted` 或“已接受”的唯一匹配行可用，普通备注、reviewer 建议或未完成 callback 不计入权威依据。

| 决定类型 | subjectDigest | 正式决定 | 决定内容与适用范围 | 后续处理 |
| --- | --- | --- | --- | --- |
| `<safe-decision-type>` | `<64 位小写 SHA-256>` | `accepted` | 不含敏感数据的裁决及适用 `RULE/caseId` | `continue` |

`contractId` 只在 Oracle 需要绑定已冻结的浏览器响应或 postcondition 查询契约时必填；DOM 与 runtime state 可以省略，不得为了通过校验虚构契约。`browser_response` 必须与唯一 `responseContractId` 一致，`postcondition_query` 必须与唯一 `queryCapabilityId` 一致；仅表示 `accepted` 的响应还必须有匹配的 postcondition Oracle，不能单独形成最终通过。

`addAssertion()` 只是可读诊断文本，不计入 Oracle 完整度或通过资格。最终 `passed` / `failed` / `unknown` 的派生及封印门禁由流程和报告规范负责，本规范只维护业务规则、来源与 Oracle 的设计映射。

#### 测试设计技术选择

测试设计技术与其适用依据必须写入同一 `plan.md` 的“测试设计技术与依据”表，并关联需求追溯编号、计划覆盖范围和 `RULE-`；阶段二由同步工具生成实际 `caseId`。不另建决策表、状态图或边界分析文档。

- **多条件业务规则**：当两个及以上独立条件的组合决定业务结果、权限或拦截行为时，必须使用决策表。表中列出条件、动作/结果、已选择的有效与无效组合及关联 `caseId`；不能用单条“组合覆盖”描述替代。
- **生命周期与状态机**：当对象存在可识别的状态、事件和转移限制时，必须使用状态迁移表或等价的 Markdown 状态图。表中列出状态、触发事件、允许/禁止的目标状态及关联 `caseId`，至少覆盖关键合法和非法迁移。
- **复杂输入**：当字段同时存在格式、长度、范围、枚举、关联字段或条件必填等约束时，必须标识等价类与边界策略；包含适用的下限前/下限/上限/上限后、非法类型或组合约束，并关联 `caseId`。阈值明确但单位换算口径未定义时，选取对合理口径都成立的明显低于/明显高于代表值，并把精确等号或相邻一单位记录为未断言；不得虚构口径，也不得让该可选精确边界阻塞同一规则的其他等价类。阈值本身未明确时记录风险依据和待确认项，不得虚构阈值。
- **用户旅程与恢复**：核心用户流程必须使用场景法，明确主成功、适用的失败、回退或重试路径；若不存在恢复语义，记录不适用依据。

技术选择按风险和需求适用性进行，不要求每个请求同时使用全部技术，也不因自动化暂不可执行而降级或省略业务覆盖。

### 5.6 覆盖完整性与覆盖层级

测试用例不得只描述正向主流程。覆盖评估以风险和适用性为先，分为两个层级：

- **测试计划或用例集层级**：先判断下表各域与本次范围是否相关，再将其标记为“适用且已覆盖”“适用待补充”或“不适用”；仅“适用”的域需要关联一个或多个用例编号。
- **单条用例层级**：只写该用例实际验证的维度，不要求机械覆盖全部维度；但每条用例都必须说明其覆盖的业务规则、状态或风险。

适用性判断应以需求承诺、业务风险、变更影响、历史缺陷、数据敏感度、集成复杂度和运行环境为依据；不能因为当前没有自动化工具就判定为“不适用”。“不适用”必须写明业务依据；“适用待补充”必须说明影响、所缺资料和是否阻塞自动化。真实设备、凭证、生产权限或外部服务受限时，不得虚构结果；应保留 `missingInfo`，并在计划中说明可用的模拟、沙箱或受控验证方式。

测试范围必须覆盖需求定义的完整业务流程及其适用阶段，不能因实现复杂、资料尚缺、环境暂不可用、需要额外脚本或存在后续执行确认而直接排除。计划“测试范围”的“包含/不包含”只写注册、登录、产品管理等顶层业务流程，不写字段规则、验证码、断言文案、原子用例拆分或 `caseId`；这些细节分别进入需求追溯、规则设计、用例和评审区块。待补事项应保留在计划中，并分别标记为“适用待补充”、受控执行或高风险动作，说明补齐条件和执行门禁；只有明确的业务不适用、用户明确排除或超出本次已确认测试请求时，才能写入“不包含”。

| 覆盖域 | 通用检查范围 | 常用设计方法 |
| --- | --- | --- |
| 业务功能与规则 | 主流程、业务分支、前置/后置条件、计算与转换规则、允许与禁止的动作。 | 场景法、决策表、因果图。 |
| 输入与数据校验 | 必填、类型、格式、长度、范围、枚举、关联字段、文件内容/元数据、非法或缺失输入。 | 等价类、边界值、组合覆盖。 |
| 状态与生命周期 | 创建、查询、修改、提交、审批、发布、撤销、删除或归档等适用状态；合法迁移、非法迁移、前后状态及可见性。 | 状态迁移图、状态覆盖。 |
| 数据完整性与一致性 | 唯一性、重复操作、幂等、并发冲突、事务原子性、失败回滚、重试、缓存/索引/列表与详情一致性、数据保留与清理。 | 幂等测试、并发场景、最终一致性轮询。 |
| 异常、容错与恢复 | 服务错误、依赖不可用、网络波动、超时、取消、中断、刷新、会话失效后的提示、可恢复性和数据安全。 | 故障注入、超时边界、恢复路径。 |
| 权限、身份与审计 | 未登录、角色权限、对象级越权、租户隔离、会话生命周期、敏感操作确认、审计记录或可追溯性。 | 角色矩阵、最小权限、负向授权。 |
| 安全与隐私 | 输入注入、敏感数据展示/传输/日志脱敏、下载与上传安全、重放/伪造防护及安全挑战边界。 | 威胁建模、负向安全用例。 |
| 接口、集成与契约 | 请求/响应契约、错误码、兼容版本、事件/消息语义、幂等键、上下游失败传播和可观察最终状态。 | 契约测试、消息语义、端到端链路验证。 |
| 兼容性与可移植性 | 浏览器、操作系统、设备、屏幕尺寸、网络条件、接口/客户端版本的支持范围与降级行为。 | 代表性矩阵、风险优先抽样。 |
| 交互、视觉与无障碍 | 信息层级、布局、响应式、可操作性、键盘操作、焦点顺序、语义/辅助技术提示、错误反馈与可读性。 | 基准视口、键盘流程、可访问性检查。 |
| 性能、容量与稳定性 | 响应时间、吞吐、并发、资源使用、长时间运行、限流、降级、恢复和容量阈值。 | 负载/压力/稳定性测试、SLO 对照。 |
| 配置、部署与可运维性 | 配置生效与回滚、特性开关、环境差异、升级兼容、监控告警、日志和故障定位所需的可观测性。 | 配置矩阵、变更前后对照。 |
| 本地化与法规要求 | 语言、时区、日期/货币/单位、字符集、区域规则、保留期限和适用的合规要求。 | 区域化数据集、规则矩阵。 |

- 业务规则、输入校验、影响下一步的阻断条件、核心状态流转、权限边界和数据一致性在相关业务中默认属于 P0 或 P1，不得因界面或接口简单而省略。
- 按风险选择覆盖深度：每次测试不必覆盖全部 13 个域，也不必覆盖所有组合；必须说明选择的等价类、边界、角色、状态或环境代表范围，以及不纳入范围的依据。
- Web/H5 的关键表单、弹窗和流程入口应至少在项目默认桌面视口验证一次视觉展示与可操作性；若产品声明支持移动端、特定浏览器、无障碍或多语言，应将相应代表范围纳入计划。
- 性能、安全、兼容性、可运维性和法规要求在存在相应需求、风险或变更时必须纳入；没有适用需求或环境时，应显式记录为“不适用”，不能因自动化能力不足而静默忽略。

### 5.7 用例集设计原则

- 用例以**可验证的业务规则或风险**为最小单位；不要按页面控件数量机械拆分，也不要把多个独立失败原因混入一条无法定位的用例。
- 正向、负向、边界、状态迁移、权限和恢复场景按第 5.5 节的拆分依据设计；可以拆成独立用例，或在同一用例中以可独立报告的子场景组织。
- 覆盖矩阵应能回答“适用的规则、状态、角色、数据边界或环境代表项由哪个用例验证”；适用项缺少关联即视为未覆盖。
- 每条确认用例必须完整映射到正式脚本、允许操作和数据资源类型；写入用例还要映射数量预算与后置验证。运行模式、数据策略、确认和台账语义分别由 [environment-guideline.md](./environment-guideline.md) 与 [automation-guideline.md](./automation-guideline.md) 维护，本规范不复制其状态表。
- Web 正式脚本必须用 `formalCase()` 注册，一条测试只绑定一个 `caseId`；禁止聚合标题、文件级串行模式和裸 `test.skip()`。同一用例的多个边界值可用软断言收集，但不同 `caseId` 必须保留独立失败与报告边界。
- 每个已确认且适用的 `caseId` 必须在正式执行清单和正式脚本中恰好出现一次，并按[报告规范](./report-guideline.md#4-执行结果标准)获得唯一原子结果。可能产生数据、前一用例失败或当前能力不足均不得成为静默省略依据；结果分类和通过资格不在本规范重复定义。
- Web/H5 工程层必须为每个正式 `caseId` 恰好映射一个环境规范定义的 `PageSessionGroup`。需要隔离的 case 也必须建立单 case 场景组并按环境规范填写隔离理由，不得用组外自由文本代替映射。同字段的异常、边界、正常用例可以在同一场景组连续执行，但仍须分别注册、断言和报告。
- 每个 case 必须独立建立前置和断言边界，不得依赖前一 case 的通过结论。`preserve_unrelated_fields` 共享组可保留其他无关输入框状态，但当前 case 必须主动设置目标字段，且不得把无关残值或提示作为本 case 证据；跨 case 业务前置只引用已声明的命名资源。
- 探索证据不得替代正式脚本覆盖；只读或零写入验证不得声称已证明写入后的业务状态。
- 需求、接口、页面、数据模型或风险变化时，应评估受影响用例并更新状态、来源、覆盖矩阵和自动化关联；失效用例不得继续作为正式覆盖证据。

### 5.8 需求追溯矩阵

每个测试计划必须在覆盖矩阵后维护“需求追溯矩阵”，将来源资料中的可验证需求映射到用例。质量覆盖矩阵用于判断测试维度，需求追溯矩阵用于证明需求没有遗漏；两者不得互相替代。

| 字段 | 要求 |
| --- | --- |
| 追溯编号 | 在计划内唯一，推荐使用 `REQ-<模块>-<序号>`。 |
| 需求来源与版本/章节 | 指向资料路径、版本和可定位的标题或章节。 |
| 优先级 | 使用资料定义的 P0/P1/P2；资料未定义时标记“未标注”。 |
| 可验证业务规则 | 一行描述可观察的行为、约束或状态，不合并无关规则。 |
| 适用性 | `适用`、`不适用` 或 `超出本次请求`；后两者必须说明业务依据或用户范围依据。 |
| 计划覆盖范围 / 派生 caseId | 计划阶段填写可验证规则、风险或场景，不得留空；阶段二由 `RULE → caseId` 关系源生成稳定用例编号。 |
| 覆盖状态 | `已覆盖`、`适用待补充` 或 `受控执行`。 |
| 缺失信息或执行门禁 | 记录环境、数据、设备、凭证、审批或其他阻塞及补齐条件。 |

- 每个适用 P0 需求在计划阶段必须关联至少一项计划覆盖范围；阶段二完成前不得声称已有关联原子用例。进入“待评审”前，每项适用 P0 需求必须经 `REQ → RULE → caseId` 派生出至少一条草案或已确认用例。高风险、环境缺失、设备不可用、需要人工确认或尚未自动化的需求，仍标记为“适用”，并使用“适用待补充”或“受控执行”。
- P1/P2 需求也必须进入矩阵；只有明确的业务不适用、用户明确排除或超出已确认测试请求，才能不生成用例。
- 单条用例的“需求追溯编号”必须回链到矩阵。需求、范围或风险发生变化时，同步更新关系源、派生视图、受影响用例和评审结论。

### 5.9 规则覆盖台账与双向门禁

新建或实质变更请求在同一 `plan.md` 使用 `结构版本：rule-coverage-v1`，把每条实际读取资料中的可测试规则拆成稳定 `RULE-<模块>-<序号>`。规则只能来自需求、原型、接口或已确认补充资料，不能由当前代码实现反推。未标记的历史计划保持告警兼容，首次实质变更时迁移；不为兼容而补造历史结论。

| 字段 | 要求 |
| --- | --- |
| 来源定位 | 实际资料的链接、章节、页面、接口字段或已确认补充定位。 |
| 规则类型 | 仅允许：业务规则、分支/决策、输入边界、异常与恢复、状态流转、页面交互、权限/身份、集成与数据一致性。 |
| 触发条件/输入、可观察预期 | 写明触发事实及用户、页面、接口或数据层可断言结果，禁止“功能正常”“符合预期”。 |
| 设计证据 | 多条件用决策表；边界用等价类/边界；生命周期用状态迁移；交互用交互断言；异常恢复用异常路径或恢复路径。 |
| 适用性与状态 | 适用、不适用、待补充、受控执行、待用户裁决均需明确；后四种必须写业务依据、执行门禁或最小裁决问题。 |
| 关联 caseId | 唯一允许人工维护的覆盖关系源；适用和受控执行规则都必须关联用例。同步工具据此生成原子用例、需求、覆盖和用例包视图。 |

`受控执行`只表示环境、数据或安全挑战阻塞执行，不免除规则、设计或用例关联。质量建议不阻塞当前验收，但必须登记为质量建议。自动演进只修复资料已明确的规则缺口；资料没有定义验收标准时保留最小用户裁决。

`task:status` 显示用例仍未生成或生成中时，门禁只校验 `REQ → RULE`、设计证据与适用性依据，不要求预先分配 `caseId`。完整性校验完成后才强制 `RULE ↔ caseId` 双向追溯；不得让计划确认后的正常用例生成被预分配编号门禁阻断。

#### 需求缺口处置与沉淀判定

产品资料写明什么，就将什么拆为可验证 `RULE` 并生成或修订用例；资料未写明的行为不得被模型推测为通过或失败预期。每个评审批次必须在同一 `plan.md` 的“沉淀判定”表，为每项发现作出唯一归属，不新建平行台账：

| 情况 | 本次处置 | 是否阻塞 | 沉淀位置 |
| --- | --- | --- | --- |
| 已引用资料明确，但 RULE、步骤或断言遗漏 | 自动修订 `RULE → caseId` 并复审。 | 不阻塞。 | 需求事实保留在 `sources → REQ → RULE → caseId`；若形成新的跨项目治理规则，只更新本规范的唯一责任区块。 |
| 资料冲突，或缺少决定当前场景预期结果的验收标准 | 记录冲突证据、受影响 `RULE/caseId`、最小待确认问题和未裁决状态。 | 仅阻塞受影响场景。 | 当前 `plan.md` 的用户裁决记录。 |
| 产品未承诺的恢复、OAuth 失败回退、弱网、安全、性能等扩展场景 | 风险登记；可提出补充建议，但不得生成带业务预期的功能用例或据此判定产品失败。 | 不阻塞已明确功能验收。 | 当前 `plan.md` 的质量建议；后续专项范围须另行确认。 |
| 明确业务不适用、用户排除或超出本次请求 | 记录不适用依据。 | 不阻塞。 | 需求追溯矩阵或规则覆盖台账。 |

“不适用”不得替代资料缺失、资料冲突或自动化困难。资料明确的缺口不得降级标为“用户裁决”或“质量建议”；质量建议不得伪装为需求覆盖缺口。

计划模板使用 `结构版本：knowledge-decision-v1` 后，每个评审批次增加以下表格。没有发现项且没有项目经验候选时填写一行“无”；存在发现项时，每项发现必须恰有一行沉淀判定。项目经验候选使用 `EXP-CAND-<序号>`，只在存在可复用的执行策略假设时登记，不得为凑表虚构候选。

| 发现项编号 | 归属类型 | 目标位置 | 证据状态 | 处理结果 |
| --- | --- | --- | --- | --- |
| <MRR-... / EXP-CAND-001 / 无> | 需求事实 / 通用规则 / 项目经验候选 / 项目经验 / 未验证推断 / 无 | <REQ → RULE → caseId / 唯一责任规范 / CAND-<编号> / docs/testing/knowledge/<project>-testing-knowledge.md / 当前 plan.md / 无> | 资料已确认 / 待受控探索或正式执行验证 / 受控探索已验证 / 正式执行已验证 / 无 | 已回链 / 已引用或已更新 / 待验证 / 已提升 / 风险登记 / 待用户裁决 / 无 |

- **需求事实**必须回链 `REQ → RULE → caseId`，不得复制到项目经验库。
- **通用规则**只引用或更新其唯一责任规范；本主题由本规范维护，不在 Skill、模板、项目经验或单个计划重复维护正文。
- **项目经验候选**在发现时必须同时登记到 `docs/testing/knowledge/<project>-testing-knowledge.md` 和 `.local/project-knowledge-candidates/<project>.json`；前者是纳入 Git 的当前经验事实源，后者只是待验证控制元数据。`plan.md` 仅写 `CAND-<编号>`、待验证状态和最小引用，不得复制候选正文。证据未满足时，正式经验条目标为“待验证”，但不得延迟登记。
- **项目经验**以“项目 + 适用范围”作为稳定键；同范围的更新观察或策略原位覆盖当前条目，旧版由 Git 历史保留。取得受控探索或正式执行证据后，只更新同一条目的证据状态和引用；计划或报告仍只保留经验库定位和验证类型。未验证经验不得被表述为已验证事实。
- **未验证推断**只可作为风险登记或用户裁决的上下文，不得成为测试断言或项目经验。

新建或实质变更请求还必须使用 `结构版本：case-relation-projection-v1`。生成或修改 RULE 关系后，使用 `npm run testcases:sync-relations -- <runtime 暂存请求目录>` 更新暂存副本并经 Activity 原子发布；对最终请求目录只运行 `npm run testcases:sync-relations -- --check <测试请求目录>`，不得绕过发布事务直接改写。历史请求未标记该版本时保持兼容告警，不迁移、不补造历史关系。

因此，`REQ ↔ RULE ↔ caseId` 的覆盖闭环只在 RULE 台账编辑一次：`REQ → RULE` 由台账字段定义，`RULE → caseId` 由同一行“关联 caseId”定义，其余视图均为派生结果。

### 5.10 用例集评审与草案演进

#### 用例包完整度

`plan.md` 只维护静态用例包边界、覆盖范围和已生成后的实际 `caseId`，不保存用例生成进度。`task:status` 可根据 workflow history、真实正文、关系、reviewer 事件和有效 callback 显示阶段，但该视图不属于测试设计资产。

- 每个计划包必须存在，所有实际 `caseId` 必须唯一落在一个包内，必填区块和内容 digest 校验通过，需求追溯矩阵回填实际 `caseId`，且用例来源回链到计划中的实际引用资料，完整性 Activity 才能成功。
- 文件存在、目录预列编号或人工声明“草案完整”都不能证明完整。正文数量、结构、唯一 `caseId`、追溯关系或 digest 任一项不满足时，不得启动 reviewer。
- 适用 reviewer 的结论和发现项闭环后才能请求用例确认；`light` 请求不创建 reviewer Activity，以完整度、关系和确定性门禁的通过记录闭环。只有绑定当前 subject digest 的 callback 为 `accepted` 且 `plan.md` 已记录正式决定，原子用例才能派生为“已确认”。

计划确认后的首份完整草案必须先通过一次结构化 readiness，再派发 reviewer。硬检查一次覆盖：计划的“输入资料”“覆盖基准与拆分清单”“需求追溯矩阵”“规则覆盖台账”和 `rule-design-matrix-v1` 标记；每个包的必填结构与唯一 `caseId`；RULE 设计矩阵；`REQ ↔ RULE ↔ caseId` 关系投影；以及每条用例来源的 manifest id、`sectionId` 和 SHA-256。任何硬缺口都在同一报告中返回并阻止评审，作者一次修订后整体复检，不交给多个 reviewer 分轮发现。

写入型用例的执行清单引用、cleanup/残留处置和未知结果核对等安全提醒也在同一 readiness 报告中汇总为 warnings；warning 用于让作者和适用 reviewer 一次看全风险，不单独阻止派发、创建 callback 或扩大已确认计划。安全边界本身仍由环境和执行授权门禁强制。

测试计划确认后，主 Agent 自动生成用例草案、完成 readiness 与用例集评审，并对资料明确的发现项自动演进和复审，直至达到“可提交确认”；中间轮次不得要求用户重复确认计划或发送“继续”。最终收敛的用例集才提交一次用户确认；每次修改尚未确认的用例集后都必须按受影响范围自动复审，不机械重跑全部角色。评审结果写入计划的“用例集评审与演进”区块，至少包括：

- 需求追溯统计（需求总数、适用需求数、已关联用例数、适用待补充数和受控执行数）。
- 规则覆盖统计（适用规则、已覆盖、受控执行、待用户裁决、不适用、无映射规则，以及按规则类型列出的缺口）。
- 覆盖域适用性复核，以及未映射需求、缺失的正向/负向/边界/状态/权限/恢复场景。
- 覆盖基准与拆分清单复核：模块/流程、输入字段、枚举/状态、关键交互和角色权限在计划阶段是否均有覆盖范围或“不适用/待补充”依据；阶段二是否已将适用覆盖范围回填为实际 `caseId`；存在 XMind 时是否记录映射差异和处理结论。
- 测试设计技术复核：适用的多条件规则、状态机、复杂输入和核心旅程是否分别采用决策表、状态迁移、等价类/边界策略和场景法，且每项都关联到 `caseId`。
- 变更影响复核：存在变更时，是否完成“来源 → 需求追溯 → caseId → 脚本/工程设计 → 复测结论”的矩阵；无影响是否有可审查依据。
- 结论：`可提交确认` 或 `需演进`；后者必须列出对应追溯编号和补充动作。

#### 真实子智能体隔离评审

新 run 的首审批次按草案结构和实际风险形成最小 `ReviewPolicy.requiredRoles`，不因测试类型机械启用全部角色：

| 风险档 | 默认角色 | 适用判断 |
| --- | --- | --- |
| `light` | 无，`deterministic_only` | `no_write` 的单一确定性字段、静态断言或导航；无认证、外部状态和高风险实际操作。 |
| `standard` | `combined` | 普通 `test` 环境新增、修改、上传、提交、删除，以及只读认证、fixture、状态迁移和复杂业务规则。 |
| `strict` | `combined`、`impact` | 实际发送 OTP、权限或设备操作、安全挑战、敏感凭据处理，或操作结果无法可靠判定。`managed_cleanup`、`tracked_residual` 和普通业务写入不得仅凭数据策略升级。 |

风险在用例包完成后按 `caseId` 计算；只读取结构化数据策略、前置条件和实际操作步骤，不从来源、排除项、`missingInfo` 或“不得发送/不提交”等否定描述推断 strict。混合用例集的最高档只用于请求摘要：`combined` 仅核对 standard/strict 用例的需求覆盖、断言依据、原子拆分、边界、状态和追溯；`impact` 仅核对 strict 用例及对应 `REQ/RULE` 和共享安全邻域。历史 run 继续使用其固定策略回放；reviewer 容量、重试和无进展停止条件由流程规范唯一定义。

reviewer 的真实隔离执行、启动方式和提示卡由 [Skill](../../skills/iot-automation-testing/SKILL.md#多角色隔离评审提示卡) 定义，并受 [automation-guideline.md](./automation-guideline.md#51-多角色隔离评审) 的阶段门禁约束。`plan.md` 是 reviewer 结论和发现项正文的唯一正式来源；`ReviewerDispatched`、`ReviewerSubmitted` 与批次失效等运行事实只写入 workflow history；reviewer/Agent 任务标识只写入可丢弃 runtime，不得进入 `plan.md` 或 history。`case-review-resolution` 只能登记 reviewer 结论和发现项，禁止修改测试范围、`REQ/RULE`、设计矩阵、关系、用例或工程内容；`case-review-evolution` 才能在已确认计划范围内修订草案并触发复审。主 Agent 是唯一汇总、演进和正式写入者；AI reviewer 的结论不是最终业务批准，最终用例确认始终由用户或测试负责人完成。

每个适用角色与新评审批次使用只读、隔离的真实子智能体；`deterministic_only` 没有适用角色，不创建子 Agent，也不伪造 `ReviewerSubmitted`。适用 Skill 已构成创建适用子 Agent 的明确授权。不得把作者推理、其他 reviewer 输出或活动文件作为输入，也不得由主 Agent 自评替代。派发和提交必须绑定宿主返回的非主任务 `agentTaskId`；任务标识只写 runtime，新提交事件只保存不含标识的隔离证明。批次快照保留完整文件作为审计回退；reviewer 默认只精读用例引用的 source section/page 和直接规则邻域，不注入整份 PDF/Word。宿主容量不足或绑定丢失时保持等待/rebind，不能降级为同一 Agent 分角色审查。

用户裁决或局部变更引发的复审采用定向范围，不得机械重跑全套审计。durable scope 必须绑定复审原因、`affectedRefs`、`baseBatchId`、受影响 `REQ/RULE/caseId` 与来源章节、规则邻域、关联数据/工程/脚本资产、明确排除引用，以及每个适用 reviewer 的最小输入集；`ReviewPolicy.requiredRoles` 只审计该范围。先用追溯关系和变更影响矩阵做全局**定位**，再只复审受影响资产；全局定位不等于重审所有用例正文。

定向批次可以复用其原 scope 完整覆盖当前未受影响链路、且变更定位能够证明该链路语义未变的已通过 reviewer 结论；每个未重审角色都必须绑定可复用证据，包括原批次、角色 Activity、输入摘要和正式计划证据摘要，缺一项就不能启动定向批次。出现新的受影响引用、共享规则邻域、数据/执行或安全边界、资料版本或草案内容时，只使对应角色证据失效并扩大必要 scope。只有跨业务域、触及核心流程/共享状态机/数据模型/安全边界，或无法证明局部影响时，才创建完整适用评审。

每个评审批次必须记录触发类型、输入基线、适用角色、隔离方式、综合结论、角色结论和发现项；reviewer 派发、提交和运行状态只在 history，宿主标识只在 runtime。批次不另存运行状态或“人工确认状态”。缺少适用 reviewer 结论时不得提交用户确认；已确认用例变化后旧确认因 subject digest 变化失效，必须完成适用复审并取得新确认。

正式记录采用单一 `REV-*` 显式边界区块，只保存输入基线、适用角色、各角色正式结论、发现项、沉淀判定和综合结论；不得保存 Agent 任务标识、派发状态、等待资源或 Activity 状态，也不另建平行“最终复审”区块。

批次正式记录完整且对应 reviewer 语义事件齐全后才算收集完成。删除 runtime 后仍须仅凭 history、`plan.md` 和真实产物重建相同业务状态。发现项未完成唯一分类与处置方式前不得自动演进；修订未登记证据、同步关系并使旧批次失效前不得启动后续复审。

reviewer 的运行与阶段交接由[流程规范的 Durable Workflow](./automation-guideline.md#314-durable-workflow生命周期与恢复)统一编排。本规范只判定评审资产是否完整：全部适用 reviewer 已原子收集、正式记录与 history 事件一致、发现项完成处置且最终复审 Activity 成功。

存在 reviewer 运行迹象但缺少对应 history 事件，或正式计划中的输入基线、角色结论与提交事件不一致时，按流程规范进入核对或阻塞。无法用 input digest、`ReviewerSubmitted` 与正式结论证明已完成隔离评审时，重新启动该 reviewer，不得根据 runtime 标识补造完成记录。

#### 证据驱动的自动演进

`需演进` 是 reviewer 的中间结论，不是把模型遗漏一律交给用户的理由。主 Agent 汇总后必须按资料证据将每项发现归入下列唯一分类，并按对应处置方式处理：

| 发现项分类 | 判断条件 | 唯一处置方式 | 对本次用例集的影响 |
| --- | --- | --- | --- |
| 需求覆盖缺口 | 已引用的需求、原型或受控资料已明确规则，但草案没有关联用例或断言。 | `自动演进` | 必须新增或修订草案、回填追溯并复审后关闭。 |
| 资料明确的设计缺口 | 已有明确规则，但原子拆分、步骤、断言、决策表、状态迁移或边界策略不足。 | `自动演进` | 必须修订草案或计划设计记录、回填 `caseId` 并复审后关闭。 |
| 业务裁决/资料冲突 | 受控资料相互矛盾，或决定预期结果的业务规则确实缺失。 | `用户裁决` | 只限制受影响场景为“适用待补充”或“受控执行”；记录最小待确认问题，不扩大阻塞整个用例集。 |
| 质量建议 | 需求没有承诺的安全、性能、弱网、OAuth 扩展失败或其他专项场景。 | `风险登记` | 记录为后续专项测试候选，明确“非本次验收阻塞”，不得伪装成需求覆盖缺口。 |

- `自动演进` 项必须在同一批次或后续复审批次中记录：已修订的 `caseId`、定位到的资料证据和“已关闭”状态。草案发生自动演进后，受影响角色的旧结论失效，必须建立新的 scope 和输入基线并运行适用 reviewer；未受影响角色只有满足定向复审证据复用条件时才能沿用。最新批次仍为“需演进”时，不得遗留“待处理”的自动演进项。
- 同一评审 epoch 最多允许两轮修改步骤、前置、预期、`REQ/RULE` 或业务语义的自动演进。第三轮仍未收敛时登记 `review_convergence_failed` 并停止派发；新的正式用户决定或受控来源证据建立新 epoch。索引、摘要、排序、格式、关系投影和 reviewer 正式记录等确定性修正不消耗轮次，也不使角色证据失效。
- `用户裁决` 项必须写出冲突资料、最小待确认问题、受影响范围和未裁决时的用例状态。它可在范围已界定时保持“待用户裁决”，但不得让未受影响的明确功能用例停留在“需演进”。
- 资料冲突只阻塞受影响断言；其余资料明确的自动演进项仍须修订、复审并收敛，不得以存在冲突为由跳过最终复审。
- `风险登记` 项必须标记为“非本次验收阻塞”，并以“已关闭”或“不适用”结束本轮评审；后续专项是否纳入由用户另行确认。
- 自动演进只修改草案，不构成用例确认，不得因此生成正式脚本或执行测试；但它也不得使稳定计划 subject 失效。用户在该阶段只处理资料冲突、未定义验收标准，或顶层业务范围、测试类型/环境、高层写入类别和权限/安全上限的实质变化，不确认普通演进轮次。

发现草案缺口时，主 Agent 应在已确认计划范围内直接新增或修订草案，再复审；直到每项适用需求均有关联用例，或具有可审查的“适用待补充/受控执行”说明。已确认用例不得静默修改；需要变更时先提出变更建议，获批后将受影响用例退回“草案”，完成演进和复审后重新确认。

自动演进的收敛只以客观证据判断：最新批次的综合结论为“可提交确认”、每个适用 `REQ → RULE → caseId` 已闭环、所有“自动演进”发现项均有资料证据与已修订 `caseId` 并已关闭、适用真实 reviewer 已完成，且静态检查没有阻止提交的失败项。综合结论仍为“需演进”时，即使发现项暂时关闭，也不得把评审任务或用例集推进到“待用户确认”。自动循环的轮次、上限、无进展阻断与对话输出由流程规范唯一维护；本规范不另定义编排步骤。

### 5.11 用例包与测试运行审核

- 计划必须维护用例包目录，列出包文件、覆盖模块、计划覆盖范围、阶段二回填的实际原子用例编号和适用的特殊门禁。不得在计划阶段仅为凑齐编号而预先规定原子用例数量。
- 用例集评审除逐条检查外，还必须检查：包内编号不重复、每个适用需求关联的编号存在、包粒度符合模块或流程边界、同一编号没有跨包重复，以及脚本/报告仍可按编号回链。`plan.md` 的用例包目录只保存静态包边界、覆盖范围和实际 `caseId`，不保存生成进度。未达到包级闭环时不得进入评审或用户确认。
- 测试运行是某次执行的不可变结果快照；运行报告至少关联计划编号、实际执行用例编号、包路径、脚本版本、环境和运行标识。运行结果、截图和日志不得写入用例包或修改用例状态。

### 5.12 变更影响分析

需求、接口、页面、数据模型、风险或工程实现发生变化时，必须在同一 `plan.md` 的“变更影响分析”记录变更来源、受影响的需求追溯编号、`caseId`、脚本/工程设计、数据或环境以及是否需要复测。变更发生后应先做全量**结构性影响定位**：复核需求追溯矩阵和覆盖基准与拆分清单是否把变化映射到完整的受影响链路；随后只重做受影响资产，不得把该定位误作全量用例复审：

1. 无业务语义变化的资料勘误，记录版本和“无受影响 `caseId`”依据；不修改已确认用例或脚本。
2. 局部业务规则、输入、状态、权限或预期变化，将受影响用例退回草案，修订、复审并重新确认；随后复核关联工程层设计、脚本、数据和复测范围。
3. 范围、核心流程、角色模型、状态机、数据模型或多数验收规则发生实质变化时，建立新的测试请求；旧请求保留为历史证据，不得覆盖其运行结论。

变更影响矩阵中的每条变更需求必须有“无影响”依据或关联至少一个受影响 `caseId`；已确认用例、脚本和运行证据不得静默覆盖。工程实现变化而业务预期不变时，业务层用例保持不变，但工程层仍须记录受影响 `caseId`、脚本和复测结论。

## 6. 标准模板

```markdown
## 测试用例：<主体>在满足<前置条件>时执行<业务动作>后获得<可验证结果>

## 基本信息

| 项目 | 内容 |
| --- | --- |
| 用例编号 | <系统>-<模块>-<序号> |
| 需求追溯编号 | REQ-<模块>-<序号> |
| 模块 | <稳定业务模块名> |
| 优先级 | P0 |
| 测试类型 | Web |
| 状态 | 草案 |
| 目标环境 | test / pre / prod（按已确认环境填写） |
| 自动化状态 | 暂不可执行 |
| 风险等级 | 低 |
| 是否需要人工确认 | 否 |

## 来源

| 资料类型 | 路径或链接 | 版本/说明 |
| --- | --- | --- |
| <需求/原型/接口/物模型/变更记录等> | <路径或链接> | <版本或说明> |

## 前置条件

- <已确认计划、环境、身份、数据、设备或依赖状态>

## 操作步骤

| 序号 | 操作 | 输入 | 预期 |
| --- | --- | --- | --- |
| 1 | <用户或系统动作> | <非敏感测试数据或占位符> | <可验证的即时结果> |

## 预期结果

- <最终业务结果、状态和必要的一致性结果。>

## 覆盖关联

| 覆盖域 | 覆盖拆分项 | 本用例覆盖内容 | 结论 |
| --- | --- | --- | --- |
| <从 5.6 选择适用域> | <字段边界/状态转换/角色动作/交互或恢复路径> | <规则、状态、边界或风险> | 已覆盖 / 不适用 / 待补充 |

> “本用例覆盖内容”必须写明来自覆盖基准与拆分清单的具体拆分项，例如字段边界、状态转换、角色动作、弹窗路径或恢复路径；不得只填写“功能正常”。

## 合理推断（assumptions）

- <推断；没有则填写“无”>

## 待补充信息（missingInfo）

- <缺失信息；没有则填写“无”>
```

模板中的 `${...}` 是测试数据占位符，不是环境变量或真实数据。生成脚本前应由 fixture、数据准备脚本或已确认配置提供实际值。

### 6.1 多阶段业务用例

- 只有真实依赖人工审核、安全接管或外部系统状态变化的业务旅程才声明多阶段；简单字段、格式、导航和可独立断言用例保持原子化，不套用等待流程。
- 多阶段用例仍绑定一个 `caseId`，但必须写清阶段顺序、每阶段可观察结果、不可重复业务动作、外部转换允许结果、恢复条件以及产生/消费的命名资源。
- 第一阶段能够在已确认清单内创建前置资源时，不得以“执行前没有已有测试数据”为由延期后续阶段；Runner 从冻结检查点继续，禁止依赖页面残值或重新提交第一阶段。
- 人工确认只证明外部状态已经发生；恢复后的登录、页面状态、下游流程和数据基线仍由自动化脚本验证。产品资料未提供申请端状态入口时，可以使用脱敏人工证明解除转换，但不得虚构查询接口或把人工证明扩大为其他产品结论。

## 7. IoT 链路补充要求

`iot-chain` 用例除通用字段外，必须在步骤、前置条件或测试数据中明确：

- 测试设备标识或可创建方式。
- MQTT Broker、Topic、Payload 结构和 QoS（如适用）。
- 消息消费、入库或告警生成的等待条件与超时时间。
- API 验证和 Web/App 展示验证。
- 测试结束后的设备状态和数据清理策略。

缺少上述信息时，自动化状态保持为“暂不可执行”，并在“待补充信息”中列出影响。

## 8. 审核清单

审核测试计划、用例集和单条用例时，至少确认：

- 测试计划、范围和目标环境是否已确认。
- 业务预期是否明确、可观察、可断言。
- 是否建立覆盖矩阵，并评估业务规则、输入与数据、状态生命周期、异常恢复、数据一致性、权限安全、集成契约、兼容性、交互无障碍、性能稳定性、可运维性及适用的本地化/法规要求。
- 是否建立需求追溯矩阵，且每项适用 P0 均关联到至少一条用例；“不适用”“超出本次请求”“适用待补充”和“受控执行”是否有可审查依据。
- 是否验证每项适用需求关联的 `caseId` 在用例包中存在、每个用例回链到计划中的需求追溯编号、无孤儿或重复 `caseId`。
- 是否在 `plan.md` 建立覆盖基准与拆分清单，并将模块/流程、输入字段、枚举/状态、关键交互和角色权限关联到 `caseId` 或记录不适用依据；存在 XMind 或人工基准时，是否保留层级映射、差异和处理结论。
- 是否在适用时记录决策表、状态迁移、等价类/边界策略和场景法依据；是否在需求或工程变化时维护变更影响矩阵和复测结论。
- 是否完成用例集评审与草案演进，并在提交确认前消除无依据的追溯缺口。
- 是否按风险完成适用 reviewer、记录角色结论与发现项闭环；自动演进后是否对新输入运行适用复审，且“可提交确认”前无待处理发现项或缺失 reviewer。执行方式与记录字段见 Skill 和流程规范。
- 是否对每项评审发现完成沉淀判定：需求事实已回链、通用规则只在责任规范维护、项目经验候选仍待验证、未验证推断未被用作断言或经验。
- 已确认用例是否在 `plan.md` 的工程层区块完成代码/图谱定位和可行性评审；代码差异是否已退回业务层确认，而非改写业务预期。
- 是否维护用例包目录；每个包是否按模块或流程组织，包内编号是否唯一，且迁移没有改变用例编号、状态或追溯。
- 报告是否以运行快照关联计划、用例编号、用例包、脚本版本和环境，而未回写测试用例定义。
- 每项已覆盖内容是否关联到具体用例；未覆盖项是否具有可审查的“不适用”或“待补充”理由。
- 是否选择了足以代表风险的等价类、边界、角色、状态、数据规模和环境，而非只验证单一正常输入。
- 是否关联正确的资料来源和版本。
- 是否包含敏感信息、生产默认操作或真实设备危险操作。
- “合理推断”与“待补充信息”是否完整，是否影响可执行性。
- 是否具备脚本生成所需的账号、数据、设备、页面/接口/Topic 信息。

## 9. Excel 交付视图

Markdown 用例包和 `plan.md` 是唯一可编辑、可版本化的测试设计源。需要人工评审、对外交付或导入测试管理平台时，可以从已确认 Markdown 单向导出 Excel；Excel 仅是交付视图，不得与 Markdown 双向编辑或作为脚本、追溯和报告的主关联依据。导出文件如需保留，应放在约定交付位置并标注对应计划、用例包和导出时间，不得创建平行用例库。

审核通过本身不直接改写状态。只有绑定当前用例集 digest 的 callback 为 `accepted`，且 `plan.md` 已保存正式用户决定后，发布事务才可把用例状态派生为“已确认”；`rejected`、`revision_requested` 或 `cancelled` 均保持“草案”，并按决定记录需修改项或取消范围。
