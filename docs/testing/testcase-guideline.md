# 测试设计与用例规范

<!-- owns: automation.testcases -->

## 1. 目的与职责

本文是测试设计索引、原子用例、追溯、评审质量和用例确认语义的唯一规则正文。

- 生命周期、Activity、callback、恢复和版本兼容由
  [流程规范](./automation-guideline.md)负责。
- 环境、数据、生产保护和清理由
  [环境规范](./environment-guideline.md)负责。
- selector 证据和报告证据分别由定位、报告规范负责。
- [Skill](../../skills/iot-automation-testing/SKILL.md)只编排读取和命令；模板只提供字段结构。

业务事实只能来自用户描述、已登记且实际读取的资料、原型/截图，或正式用户补充。源码和运行页面是工程证据，不得反推资料未定义的业务规则。

## 2. v7 设计资产

新建或实质变更请求使用：

- `plan.md`：`test-design-index-v2`、`rule-design-ledger-v2`、
  `case-relation-projection-v2`；
- `cases-*.md`：`testcase-v2`。

v5/v6 请求继续按历史定义和原结构恢复，不批量迁移，也不改写既有确认或评审记录。

### 2.1 `plan.md` 的唯一内容

`plan.md` 是内部测试设计索引，不是单独提交用户确认的测试计划。它只维护：

1. 基本信息、顶层范围和实际来源；
2. 环境、静态资产、数据和安全边界；
3. 需求索引；
4. 唯一规则设计台账；
5. 用例包目录、变更影响、假设、缺口和风险；
6. 单一评审记录、正式用户决定；
7. 用例确认后的工程映射。

运行阶段、Activity 状态、重试、等待、阻塞、完整度和工作流终态不得写入 `plan.md`。这些事实只从 `workflow-history.ndjson` 和真实产物派生。

新结构禁止重新创建以下平行区块：

- 覆盖基准与拆分清单；
- 覆盖矩阵或独立需求追溯矩阵；
- 独立规则覆盖台账、规则设计矩阵或规则邻域复核；
- 用例集评审汇总、预计交付物和重复的测试方式。

### 2.2 范围、来源与边界

“测试范围”只写顶层业务流程及用户明确排除项。字段规则、输入边界、状态分支和断言进入规则设计台账；环境暂不可用、缺少设备或自动化困难不能写成业务“不包含”。

每项被引用资料必须记录稳定来源 ID、可点击路径、版本或 SHA-256、精确章节/页面/字段及用途。索引命中但未读取的资料不是依据；静态测试资产是 build 输入，不是需求来源。

环境、数据和安全边界只记录本请求已确定的选择与未决门禁，不复制环境规范。用例确认不授权业务写入、设备动作、生产访问或安全挑战处理。

## 3. 需求索引与规则设计台账

### 3.1 需求索引

每条可验证需求使用稳定 `REQ-<模块>-<序号>`，并记录来源、资料优先级、单一可验证需求和适用性依据。资料没有给出优先级时标为“未标注”，不得由模型补造。

### 3.2 `rule-design-ledger-v2`

规则设计台账是 `REQ → RULE → caseId` 的唯一关系源。每一行是一条原子规则，必须包含：

- 稳定 `RULE-<模块>-<序号>` 和关联 `REQ`；
- 来源定位与适用覆盖域；
- 触发条件、输入边界和可观察预期；
- 设计技术；
- 数据/执行门禁；
- 有序关联 `caseId` 和结论。

规则只允许来自业务资料或正式用户补充。可观察预期必须说明页面、接口、消息或数据层能够看到的结果，禁止“功能正常”“符合预期”。资料未定义时明确写“未定义，不生成断言”，并作为待确认项进入同一次用例确认。

适用规则必须关联至少一个用例；`受控执行`只限制执行，不免除设计和用例覆盖。`不适用`必须有业务依据；环境受阻、实现困难和资料缺失都不能冒充不适用。

### 3.3 设计技术

按真实规则选择技术，不要求机械套用全部方法：

- 多条件决定结果时使用决策表；
- 明确上下限、格式或枚举时使用等价类和边界值；
- 存在状态和合法/非法转移时使用状态迁移；
- 核心成功、失败、回退或重试路径使用场景法；
- 权限、租户和角色差异使用角色/资源矩阵。

技术和关键组合直接记录在规则台账，不再建立平行设计矩阵。

## 4. 原子用例结构

`testcase-v2` 的每条用例只包含：

1. 基本信息；
2. 来源；
3. 前置条件；
4. 步骤；
5. 预期结果；
6. 假设与待确认项。

基本信息保留 `caseId`、`REQ`、`RULE`、模块、优先级、测试类型、目标环境、数据策略和风险等级。用例正文不得保存自动化状态、是否需要人工确认、重复覆盖表、评审回链、运行状态或结果。

每个 `caseId` 必须全请求唯一，并对应一个可独立报告的行为。多个无关失败原因不得塞入同一用例；同一规则的连续步骤可以保留在一条用例中，但每个预期都必须能定位到步骤或最终状态。

步骤只描述用户或系统可观察行为，不包含 selector、代码路径、框架调用和秘密值。前置条件说明可验证基线、数据预算及清理/残留安排；写入能力当前不可用不等于删除该用例。

预期结果必须来自资料或正式用户决定。HTTP 2xx、页面提示、截图或 ARIA 只能证明其直接观察，不能自动证明后端写入、消息送达或设备状态成功。

## 5. 质量与追溯门禁

### 5.1 来源忠实性

用例来源必须能回到设计索引中的实际资料。代码、测试脚本、DOM 或接口实现只能帮助定位和实现，若与资料冲突，应登记差异并提交业务确认，不能静默改写预期。

### 5.2 双向关系

关系同步后必须同时满足：

- 每个适用 `REQ` 至少有一个 `RULE`；
- 每个适用/受控 `RULE` 至少有一个真实 `caseId`；
- 台账中的 `RULE → caseId` 与用例基本信息中的 `caseId → RULE` 完全一致；
- 每个用例只存在于一个声明的用例包；
- 用例中的 `REQ` 是其全部关联 `RULE` 的需求并集。

`npm run testcases:sync-relations -- <暂存请求目录>` 只生成派生关系；最终请求目录使用 `--check`。作者只编辑规则设计台账的关联 `caseId`，不得在多个矩阵重复维护同一关系。

### 5.3 用例集设计原则

- 主成功、适用失败、边界、状态、权限、恢复和一致性场景按需求风险选择，不以固定用例数量为目标。
- 资料定义的 P0/P1 规则不得因自动化受阻而省略；受阻信息进入数据/执行门禁。
- 每条用例独立建立前置和断言边界，不依赖前一用例“通过”。跨用例依赖只通过已声明命名资源表达。
- 需求、环境边界或风险变化时，先计算受影响 `REQ/RULE/caseId`；无关用例不得失效。

### 5.4 完整度

文件存在、目录预列编号或作者声明“草案完整”都不是完成证据。完整度由真实正文数量、必填区块、唯一 `caseId`、来源、规则台账和双向关系确定性计算。任一项缺失时不得请求 reviewer 或用例确认。

### 5.5 需求缺口处置与沉淀判定

- 资料明确但设计或用例遗漏：自动补齐，重新同步、校验和复审。
- 资料冲突或缺少决定预期的验收：保留证据、受影响引用和最小问题，进入同一次用例确认。
- 产品未承诺的扩展恢复、安全或性能行为：只登记风险或建议，不生成带虚构预期的功能用例。
- 明确业务不适用或用户排除：记录依据，不生成用例。

需求事实留在 `sources → REQ → RULE → caseId`；通用规范留在唯一责任文档；项目经验只保存在对应项目经验库。三者不得相互复制。

### 5.6 变更影响

`affected_rebuild` 只能覆盖确定性计算出的受影响 `caseIds` 和关联规则，并继续绑定未变化的全局范围、环境、数据和安全边界。全局边界变化、影响映射不完整或存在跨范围冲突时必须回退 `full_replan`。

### 5.7 工程映射

只有用例确认 `accepted` 后才能填写工程映射。该区块只记录 `caseId` 与仓库/图谱、脚本、定位和断言证据、环境/数据前置及实现差异的映射；不得反向修改业务规则、步骤或预期。

## 5.10 用例集评审与草案演进

首稿必须先通过完整度、来源、规则设计和关系门禁，再进入评审。评审输入固定为实际来源、当前设计索引、用例包和确定性检查摘要；reviewer 只读且彼此隔离。

### reviewer 适用性

- `deterministic_only`：低风险且全部确定性门禁通过，不创建 reviewer Activity；
- `combined`：需求一致性、用例设计和追溯；
- `impact`：数据写入、权限、安全挑战、设备动作、清理和变更影响。

评审记录只保留最新输入摘要、适用 reviewer 与依据、结论、发现和处置摘要。派发、重试、等待、失效和工具任务标识不写入 `plan.md`。

### 收敛规则

- 有资料证据的缺口由自动演进修订，并重新运行完整度、关系和适用复审；
- 资料冲突、未定义验收或用户补充不再创建独立“业务裁决” callback，统一进入用例确认；
- 质量建议不阻塞资料已定义的用例确认，但必须标明不属于当前验收；
- 并发、重试、演进轮次和中断恢复只由流程规范决定。

## 6. 用例确认语义

v7 没有独立计划确认。设计、校验和评审收敛后只提交一次测试用例确认：

- `full_replan`：确认全部有序 `caseIds`、语义摘要和全局边界；
- `affected_rebuild`：只确认 `affectedCaseIds` 及关联规则，同时绑定未变化的全局边界；
- `direct_execute`：复用已确认稳定设计，不重复确认用例。

`case-confirmation-subject-v2` 必须绑定请求、full/affected 范围、suite 版本、有序用例语义、范围/环境/数据/安全边界、关联 `REQ/RULE`、来源、未决项和最新评审摘要。

摘要失效规则：

- 用例语义、规则、范围、环境、数据/安全边界、相关风险或评审结论变化会失效；
- 正式决定表、运行状态和确认后的工程实现变化不会污染摘要；
- affected 摘要忽略无关用例变化，但任何全局边界变化都拒绝定向流程。

v7 只允许：

- `accepted`：进入 build；
- `revision_requested`：记录用户补充，失效相应生成/评审结果，自动修订后重新提交同一种用例确认；
- `cancelled`：取消请求。

`rejected` 仅供旧定义回放。用例确认只批准设计内容，不批准业务写入、设备操作或生产执行；这些权限继续由独立执行清单确认控制。
